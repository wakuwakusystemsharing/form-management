# 予約フォーム「更新して他のフォームにも反映」実装設計

作成日: 2026-10-08

## 目的
同じ店舗に LINE 予約フォームと Web 予約フォームがあり中身がほぼ同じとき、片方を編集した内容をもう片方へ 1 回の操作で反映し、更新（デプロイ）まで済ませる。これまでは両方を同じ内容で編集していたため工数が 2 倍だった。

## 決めたこと（2026-10-08）
- 反映先は **同じ店舗の予約フォーム** に限定（アンケート・抽選・他店舗は対象外）
- **「送信時の項目編集」（`line_message_items`）は同期しない**（LINE と Web で項目を変えている店舗があるため）
- 反映先の **再デプロイは自動**（保存だけで止めない。失敗したときだけ結果一覧で案内）

## 方式: コピー同期（案 1）
親子リンク（自動追従）や 1 フォームから 2 種別を生成する方式ではなく、「保存時に選んだ範囲を選んだフォームへコピーして更新する」方式。既存の保存・デプロイ API をそのまま使うため、認証・正規化・操作履歴は通常の更新と同じ。

## 画面
- フォーム編集モーダル（`FormEditModal.tsx`）のヘッダー下、「更新」の右に **「更新して他のフォームにも反映」**（予約フォームのみ表示）
- 押すと、まず編集中のフォームを保存＆デプロイ（従来の「更新」と同じ）。成功したら `FormSyncDialog` を開く
- ダイアログ（`src/components/FormEditor/FormSyncDialog.tsx`）
  - 反映先: `GET /api/stores/{storeId}/forms` から同じ店舗の予約フォーム（元以外）をチェックで選択。LINE / Web と公開状態のバッジ。前回の選択を端末に記憶（localStorage `form_sync_targets_{sourceId}`）
  - 反映する内容: 下表のセクション（既定すべて ON）
  - 「N 件に反映して更新」→ 反映先ごとに 取得 → 差し替え → 保存 → デプロイ。結果を一覧で表示

## 反映する内容（セクション）
| ID | 画面上の名前 | コピーする項目 |
|---|---|---|
| `basic_display` | 基本情報（共通部分） | `basic_info` のうち フォーム名 / LIFF ID / LINE 以外の制限 / 2 通目メッセージ **以外** |
| `menu_structure` | メニュー構成 | `menu_structure` 全体 |
| `selections` | 詳細設定（性別・ご来店回数・クーポン・スタッフ選択） | `gender_selection` / `visit_count_selection` / `coupon_selection` / `staff_selection` / `visit_options` |
| `custom_fields` | カスタム項目・画像 or テキスト設置 | `custom_fields` / `content_blocks` |
| `calendar_settings` | 営業時間・受付ルール・日時選択 | `calendar_settings`（`show_customer_email` / `notification_email` **以外**）/ `manual_form_settings` / `validation_rules` |
| `cancel_rules` | キャンセルルール設定 | `cancel_rules` |
| `notification_messages` | 通知メッセージ | `notification_messages` |
| `display_settings` | ご予約内容・表示設定 | `reservation_summary` / `ui_settings` |

常に反映先のまま: `form_type`、`line_message_items`、上記の除外項目。

## 処理の流れ（クライアント側で順に実行）
1. `GET /api/forms/{targetId}`（最新の反映先を取得。`store_id` が同じ店舗か確認）
2. `buildSyncedConfig(source.config, target.config, sections)`（`src/lib/form-sync.ts`。純粋関数・Vitest）
3. `PUT /api/forms/{targetId}` に `{ ...target, config }`（フォーム全体。通常の保存と同じ経路で正規化・操作履歴）
4. `POST /api/forms/{targetId}/deploy`（通常の「更新」と同じ）
5. 成功 / 失敗を一覧表示（保存成功・デプロイ失敗は区別して表示）

## 元に戻す（スナップショット）— 2026-10-08 追加
- テーブル `form_config_snapshots`（`20261008000000_add_form_config_snapshots.sql`）: 店舗 ID / フォーム ID / config 全体 / reason（update / sync / restore）/ reason_label / source_form_id / 操作者 / 日時。RLS 有効・ポリシー無し（service_role 経由のみ）。フォームごとに直近 20 件を保持（`MAX_SNAPSHOTS_PER_FORM`）
- 保存のタイミング（いずれも上書き直前）: 「更新」（reason = update）、「他のフォームにも反映」の反映先（sync。「○○」から反映前）、復元（restore。復元前）
- API: `GET /api/forms/{id}/snapshots`（一覧・config なし）/ `POST`（現在の config を保存）/ `GET /api/forms/{id}/snapshots/{snapshotId}`（config 付き。正規化済み）。認可は店舗アクセス
- 復元はクライアント側（`restoreFormFromSnapshot` in `FormSnapshotDialog.tsx`）: 復元前を保存 → スナップショットの config で `PUT /api/forms/{id}`（`form_type` は現在のまま）→ `POST .../deploy`。復元前も保存するので「戻したのを取り消す」ができる
- 画面: 反映結果の各行に「元に戻す」（反映直前の状態へ）。編集モーダルの「更新履歴」ボタン → 一覧（日時・理由・操作者）、「現在との違いを見る」で変わるセクション名を表示、「この状態に戻す」→ 確認（これより新しい N 件の変更も消える旨）→ 戻して更新
- 戻すのは config のみ。フォーム ID・種別・公開 URL・デプロイ情報・公開状態は変えない。自動で巻き戻す仕組みは作らない（必ず人が選ぶ）

## 注意点・今後
- 反映は上書き。元に戻すときは反映結果の「元に戻す」か、編集モーダルの「更新履歴」から
- 親子リンク（自動追従）が必要になったら、この同期を「保存時に自動実行する設定」として乗せる
- セクションを増やすときは `FORM_SYNC_SECTIONS` と `buildSyncedConfig` の両方を更新し、テスト（`form-sync.test.ts`）に除外項目の保持を追加する
