## 2. Vercel / Supabase で障害が起きないか

### 結論

**今の使い方と規模なら、4 機能とも Pro プランの範囲で動きます。**
ただし ④ 1対1トークだけは、作り方を間違えるとデータ量とアクセス数が大きく増えるので、設計で抑えます（下の「④ で気をつける数字」）。

### 今の本番の状態（2026-11-20 に読み取り専用で確認）

| 項目 | 今の値 | Pro プランの枠（※） | 余裕 |
|---|---|---|---|
| データベースの大きさ | 65 MB | 8 GB | 十分 |
| Storage（フォームの HTML・画像） | 106 MB（627 ファイル） | 100 GB | 十分 |
| 店舗数 | 216（うち LINE 設定あり 108） | — | — |
| 予約 / 顧客 | 3,704 件 / 1,815 人 | — | — |
| 定期実行（pg_cron） | 6 本（5 分おき 1 / 10 分おき 2 / 毎時 3） | — | 1〜2 本増えても問題なし |
| DB の同時接続の上限 | 60 | — | アプリは API 経由で読むので、接続数は増えにくい |
| API の制限時間（`vercel.json`） | 30 秒 / メモリ 1024MB / 東京 | — | 設定どおり |

※ 枠の数字はこの資料を書いた時点で把握している一般的な値です。料金体系は変わることがあるので、**④ を作り始める前に、Vercel と Supabase の管理画面（Usage / Billing）で実際の枠と今月の使用量を確認します**。

### 機能ごとの影響

| 機能 | Vercel | Supabase | 判定 |
|---|---|---|---|
| ① 流入経路 | QR を読むたびに 1 回の軽いアクセス | 小さな表が 1 つ増える | 問題なし |
| ② カレンダー | 画面を開く・月を変えるたびに 1 回 | 既存の予約を読むだけ | 問題なし |
| ③ リッチメニュー | 保存のときだけ LINE と通信 | 画像は 1 枚 1MB まで | 問題なし |
| ④ 1対1トーク | 新着の確認で、開いている間ずっとアクセスが続く | 会話と画像が増え続ける | **設計で抑える** |

### ④ で気をつける数字

**(1) 画像の容量**
お客様が送る写真は 1 枚 2〜5MB あります。そのまま保存すると、多い想定（100 店舗 × 1 日 5 枚 × 3MB）で 1 年に約 550GB になり、枠（100GB）を大きく超えます。

→ 対策: 保存するときに長辺 1600px の JPEG に縮めます（1 枚 約 200〜300KB）。同じ想定で 1 年 約 40〜55GB に収まります。あわせて保存期間（1〜3 年）で自動削除し、既定 OFF なので実際に増えるのは ON にした店舗のぶんだけです。

**(2) 会話の行数**
多い想定（100 店舗 × 1 日 50 通）で 1 年に約 180 万行、約 1GB です。枠（8GB）に収まりますが、3 年保存の店舗が多いと 3GB を超えます。

→ 対策: 保存期間での自動削除、店舗 ID と日時の索引、月 1 回の容量確認。

**(3) 新着確認のアクセス数**
トーク画面を開いている間、新着を確認し続けます。50 店舗が 1 日 8 時間、10 秒おきに確認すると 1 か月で約 430 万回です。

→ 対策: 確認は 15 秒おき、タブが見えているときだけ、新着が無い間は間隔を 30 秒まで延ばす。これで約 3 分の 1 になります。それでも多ければ Supabase の Realtime（新着を押し出して知らせる仕組み）に切り替えます。最初から Realtime にしないのは、権限の設定を間違えると他の店舗の会話が見えてしまう事故につながるためです。

**(4) LINE からの通知（Webhook）の応答時間**
LINE は応答が遅いと通知を送り直します。今も Webhook の中で多くの処理をしているので、④ で会話の保存と画像の取得を足すと遅くなります。

→ 対策: 画像の取得・縮小・通知は、LINE に応答を返したあと（`after()`）に行います。

### staging の制限（4 機能すべてに関係）

staging の Vercel はログイン保護（Deployment Protection）があり、**外からのアクセス（LINE の Webhook、LINE が画像を取りに来るアクセス、cron）が届きません**。

- ③ ④ は「LINE から届く」「LINE に画像を渡す」が中心なので、staging だけでは最後まで確認できません
- **③ ④ は、本番のデモ店舗で確認します**（決定）。本番に出してから確認することになるので、次の 2 つで事故を防ぎます
  - 新しい機能は必ず「店舗ごとに OFF が既定」にし、デモ店舗だけ ON にして確認してから他の店舗に広げる
  - LINE と通信しない部分（保存・判定・画面）は、local とテストで先に確かめておく

## 3. 4 機能に共通するルール

これまでの機能で実際に起きた不具合から決めたルールです。4 機能すべてで守ります。

### データの読み書き

- **API はすべて `authorizeStoreAccess`（店舗単位の権限確認）を通す**。画面でボタンを隠すだけにしない。「弊社だけが変えられる設定」は API 側でも役割を確認する
- **1000 件の壁**: Supabase は 1 回の取得が 1000 件までです。一覧・集計は `fetchAllRows`（1000 件ずつ全件）か、期間で絞って取得します（集計ダウンロードで件数が欠けた不具合の再発防止）
- **日付は日本時間**: 日付だけの値（`2026-11-20`）は文字列のまま扱い、`new Date('2026-11-20')` にしません（9 時間ずれて前日になる）。月の集計は `toJstDate` を使います
- **local（JSON）でも動くようにする**: 新しいデータは `data/*.json` に保存し、LINE との通信は local では行いません
- **LINE ユーザー ID を画面・API に返さない**: 画面にはこのシステムの ID（顧客 ID・スレッド ID）だけを渡します

### DB の変更（マイグレーション）

- staging / production へは **Dashboard の SQL Editor で手動適用**します
- **適用前でも既存の機能が動くように作る**（列が無いときは列なしで読み直す。配信・分岐で使っている書き方）
- cron の登録はマイグレーションに含めません（本番だけ Dashboard から登録）

### お客様のフォーム（静的 HTML）に手を入れるとき

- 保存＆デプロイしていないフォームは古い HTML のままです。**新しい機能を前提にするときは `static_deploy.features` に印を付け、印の無いフォームでは機能を出さない**（「メニューを変更」で、古い HTML が通常の予約として送信してしまう事故を防いだ方法）
- 埋め込む JavaScript はバッククォートを使わず、設定は `<` にエスケープして埋め込みます

### 二重送信・二重保存

- ボタンは押した直後に無効にする（アンケートの連打で回答が重複した事例）
- 「状態を先に書き換えてから送る」（空き待ち・リマインダーで使っている方法）。送ってから記録すると、途中で止まったときに二重に送ります
- LINE への送信には `X-Line-Retry-Key`（同じ鍵なら LINE 側で 1 回にまとめる）を付けます

### 作り方

- 計算・判定は「純粋ロジック」（`src/lib/*.ts`。DB にも画面にも触らない関数）に分け、先にテスト（Vitest）を書きます
- 文言は初心者にも分かる言葉にし、「このページの使い方」（`src/lib/store-admin-guide.ts`）にも足します
- 新しいタブ・項目は「店舗管理者に表示するメニュー」（`store-admin-tabs.ts`）で店舗ごとに出し分けられるようにします
- 1 つの PR は 1 つの目的にし、PR ごとに 型チェック・ESLint・全テストを通します
- CLAUDE.md と `docs/API_SPECIFICATION.md` を機能ごとに更新します

## 4. 先に直しておくこと（Webhook の署名チェック）

### 見つかったこと

`POST /api/webhooks/line`（LINE からの通知を受け取る入口）は、**送り主が本当に LINE かを確認していません**。
CLAUDE.md には「署名検証あり」と書かれていますが、コードには署名を確認する処理がありません（確認する処理があるのはメール受信の Webhook だけです）。

### なぜ今回困るのか

URL に付いている `storeId` を知っていれば、誰でも「お客様からメッセージが来た」という偽の通知を送れます。
今も良くない状態ですが、④ 1対1トークを入れると、**偽のメッセージがトーク画面に本物として表示される**ようになります。③ でも、偽の操作でお客様ごとのメニューを切り替えられてしまいます。

### 直し方

1. `stores.line_channel_secret`（チャネルシークレット）の列を足し、テナント側の店舗編集で登録できるようにする
2. Webhook は、届いた内容そのもの（文字列のまま）とシークレットから計算した値を、ヘッダー `x-line-signature` と比べる（一致しなければ 401）
3. **段階的に入れる**（一気に必須にすると、シークレット未登録の 108 店舗の Webhook が全部止まる）。運用は「トークを使うと決まった店舗に、弊社が手動でシークレットを登録 → 接続を確認 → トークを ON」の順

| 段階 | 動き |
|---|---|
| 第 1 段階 | シークレットが登録されている店舗だけ確認する。未登録の店舗は今までどおり通す。不一致はログに残す |
| 第 2 段階 | ③ のお客様ごとの切り替え・④ トークは、**シークレットが登録されている店舗でしか ON にできない** |
| 第 3 段階 | **行わない**（全店舗の必須にはしない。未登録の店舗は今までどおり動かす） |

### 注意点

- 今のコードは `req.json()` で読んでいます。署名の計算には「届いた文字列そのまま」が必要なので、`req.text()` で読んでから JSON に直す形に変えます（読み直すと 1 文字でも変わると不一致になる）
- 比較は `timingSafeEqual`（時間差で推測されない比べ方）を使います
- シークレットを間違えて登録すると、その店舗の予約確認・キャンセルなどの LINE 応答がすべて止まります。**登録画面に「接続を確認」ボタン**を付け、LINE の「Webhook の検証」ボタンが通ることを確かめてから保存を勧めます
- シークレットは画面に再表示しません（登録済みかどうかだけ表示）

## 5. ① 流入経路の計測

### どんな機能か

店頭ポップ・チラシ・Instagram など、**置き場所ごとに別々の URL と QR コードを発行し、どこから予約が入ったかを数えます**。

```
店舗が「店頭ポップ」という経路を作る
  → 専用の URL と QR コードができる
  → お客様が QR を読んで予約する
  → 予約に「店頭ポップ」と記録される
  → 経路ごとの 読まれた数 / 予約数 / 売上 が見える
```

### 今あるもの

- `reservations.source_medium`: Web 予約フォームだけ、開いた元のサイトから自動で推測して記録しています（LINE / Instagram / Google 検索など 8 種類の固定値）
- 自動の推測なので、「店頭ポップ」と「チラシ」のような店舗独自の区別はできません。LINE フォームでは記録していません

### 追加するもの

**データ**

| 表 / 列 | 内容 |
|---|---|
| `reservation_sources`（新しい表） | 店舗 ID / 経路の名前 / 合言葉（`code`。6 文字のランダム）/ 開くフォーム / 有効かどうか / 読まれた数 |
| `reservations.source_code`（新しい列） | その予約の経路の合言葉。無ければ null |
| `customers.first_source_code`（新しい列） | その顧客が最初に予約したときの経路（空のときだけ入れる） |

既存の `source_medium` はそのまま残します（消さない・意味を変えない）。

**URL の形**

- 発行する URL: `https://（このシステム）/s/{code}`
- 開くと「読まれた数」を 1 増やし、予約フォームへ移動します
  - LINE フォーム: `https://liff.line.me/{liffId}?src={code}`
  - Web フォーム: 公開 URL に `?src={code}`
- 一度このシステムを通すので、あとから開くフォームを変えても、印刷済みの QR はそのまま使えます

**画面**

- 予約管理 →「分析」の中に「流入経路」を追加
- 経路の一覧（名前 / QR / URL のコピー / 読まれた数 / 予約数 / 予約率 / 売上）、追加・名前の変更・停止
- QR コードは既存の `qrcode` パッケージで作り、画像としてダウンロードできるようにします

**API**

- `GET/POST /api/stores/{storeId}/reservation-sources`、`PUT/DELETE .../{id}`
- `GET /api/stores/{storeId}/reservation-sources/stats?date_from&date_to`
- `GET /s/{code}`（公開。数えて移動するだけ）
- `POST /api/reservations` に `source_code` を追加

**純粋ロジック**（`src/lib/reservation-sources.ts`）

- `computeSourceStats(reservations, sources, period)`: 経路ごとの 予約数（キャンセル除く）/ キャンセル数 / 売上（`reservationAmount`）。経路なしは「経路なし」にまとめる
- `resolveSourceCode(入力, 店舗の経路一覧)`: 店舗に無い合言葉は null にする

### 注意点（バグになりやすい所）

| # | 起きうること | 対策 |
|---|---|---|
| 1 | **古い HTML のフォームは `?src=` を知らない**。QR から予約しても経路が記録されず、「0 件」に見える | デプロイ時に `static_deploy.features` に `source` の印を付ける。印の無いフォームを開く経路には、一覧に「このフォームを保存＆デプロイしてください」と警告を出す |
| 2 | LINE フォームは URL の付け足しが `liff.state` という形で届く | 「メニューを変更」（`?change=`）と同じ読み方（`getChangeReservationId` と同じ方式）を使う |
| 3 | お客様が URL を書き換えて、でたらめな合言葉を送る | サーバーで、その店舗に存在する合言葉かを確認。無ければ null（予約は成功させる） |
| 4 | 経路を削除すると、過去の集計が消える | 削除ではなく「停止」にする。停止した経路は URL を開くと通常のフォームへ移動し、集計には残す |
| 5 | QR を読んだだけで閉じた人、検索ロボットのアクセスで「読まれた数」が増える | 数は目安として表示（「予約率」は参考値と注記）。ロボットらしいアクセス（User-Agent）は数えない |
| 6 | 手動予約・「予約を変更」・「メニューを変更」で経路が上書きされる | 経路を入れるのは新しい予約を作るときだけ。変更では触らない |
| 7 | 経路の名前に記号を入れられて画面が崩れる | 名前は 40 文字まで。表示はエスケープ |
| 8 | 複数フォームがある店舗で、どのフォームの予約か分からなくなる | 経路 1 つにつき開くフォームは 1 つ。集計はフォームで絞り込める |

### 集計の決まり（①-2 で実装）

| 項目 | 決まり |
|---|---|
| 期間 | **予約日**で数える（分析のほかのタブと同じ。上の期間とフォームの絞り込みをそのまま使う） |
| 予約数・売上 | キャンセル済みを除く。キャンセルは別の列に出す |
| 経路なし | 経路の URL を通らずに入った予約（公式 LINE のメニューから開いた予約、経路を作る前の予約、店舗側で入力した予約など） |
| 読まれた数 | これまでの累計（日ごとの記録は持っていない） |
| 予約率 | これまでの予約（キャンセルを含む）÷ 読まれた数。期間に関係なく累計で出す。目安 |
| 停止した経路 | 集計に残す（「停止中」と表示） |

設計から変えた点: `customers.first_source_code` の列は作っていません（必要になったら予約の記録から出します）。合言葉は 8 文字です。

### 友だち追加の経路（今回は作らない。設計だけ）

LINE の仕様で、友だち追加の通知には「どの QR から来たか」が入りません。測るには次の流れが必要です。

```
QR → このシステムのページ（LIFF）を開く → LINE のユーザーを確認して経路を記録 → 友だち追加の画面へ
```

- お客様の操作が 1 タップ増えます
- LIFF と公式 LINE が同じプロバイダーにある必要があります（違うと ID が食い違う。2026-11-20 のデモ店舗の調査で実際に起きていた問題）
- 予約の経路を使ってみて、必要と判断してから作ります

|---|---|---|
| ①-1 | 表と列、経路の発行画面、`/s/{code}`、フォームが `source_code` を送る、サーバーで記録 | local で QR の URL を開く → 予約 → 予約に経路が入る。古い HTML では警告が出る |
| ①-2 | 経路ごとの集計画面（予約数・売上・読まれた数） | 期間・フォームで絞り込める。停止した経路も集計に残る |

## 6. ② カレンダー

### どんな機能か

**予約を 日 / 週 / 月 のカレンダーで見て、その場で開いたり動かしたりできる画面**です。

### 置き場所

**独立したタブ「カレンダー」を作り、予約管理タブからも開けるようにします**（決定）。

- タブの ID は `calendar`。「店舗管理者に表示するメニュー」（`store-admin-tabs.ts`）に足し、店舗ごとに出し分けられるようにします
- 予約管理タブには「カレンダーで見る」ボタンを置き、同じ画面（`?tab=calendar`）へ移動します。画面を 2 つ作らず、部品は 1 つです
- **予約管理タブを非表示にしている店舗では、カレンダーも既定で非表示にします**（予約を見せない設定の店舗で、カレンダーから予約が見えてしまうのを防ぐ）。カレンダーだけ見せたい場合は個別に ON にできます
- テナント側の店舗ページと店舗管理者ページで同じ部品を使います

### データ

**新しい保存先は作りません。**

- 予約: 既存の `reservations`（このシステムの予約が正）
- 予約以外の予定（Google カレンダーに直接入れた「休み」「打ち合わせ」など）: 既存の空き状況 API と同じ読み方で取り、灰色の帯で表示します。**タイトルは「予定あり」とだけ出します**（個人的な予定の中身を管理画面に出さないため）

**API**

- `GET /api/stores/{storeId}/reservations/calendar?from&to&staff_id`（期間は最大 62 日。その期間の予約だけを返す）
- 日時の移動は、既存の `PATCH /api/reservations/{id}` を使います（Google カレンダーの予定の更新・来店履歴・フォローメッセージ・空き待ちの見回りは、既にこの中で行われています）

**純粋ロジック**（`src/lib/reservation-calendar.ts`）

- `toCalendarEvents(reservations)`: 予約 → 画面に置く帯（開始・終了・色・表示名）
- `layoutDayEvents(events)`: 同じ時間に重なる予約を横に並べる計算
- `moveTarget(drop位置, 時間間隔)`: 落とした位置 → 日付と時刻（時間間隔に丸める）

### 部品の作り方

**既製のカレンダー部品は使わず、最初から自作します**（決定）。見た目を管理画面にそろえやすく、スタッフごとの列も自由に作れます。そのぶん、次の 3 つを自分たちで正しく作る必要があります。

| 自作する部分 | 内容 | 確かめ方 |
|---|---|---|
| 日付の並び | 月の 1 日が何曜日か、前後の月の日をどこまで出すか、週の始まり | 純粋ロジック `buildMonthGrid(year, month)` にして、うるう年・月末・年またぎをテスト |
| 重なりの配置 | 同じ時間に重なる予約を横に並べ、幅を分ける | 純粋ロジック `layoutDayEvents(events)` にして、2 件・3 件・入れ子の重なりをテスト |
| ドラッグ | 帯をつかんで別の日時に落とす。落とした位置 → 日付と時刻 | 位置の計算は純粋ロジック `moveTarget`。つかむ・落とす操作はブラウザ標準の仕組み（Pointer Events）で作り、PC だけ有効にする |

- 日付の計算に `Date` の足し算（+24 時間）を使いません。年・月・日の数字で計算します（タイムゾーンの変換が混ざるとずれるため）
- 画面の描画が重くならないよう、月表示は 1 日に出す予約を 3 件までにして「ほか N 件」にまとめます

### 注意点（バグになりやすい所）

| # | 起きうること | 対策 |
|---|---|---|
| 1 | **日付が 1 日ずれる** | 日付は文字列（`2026-11-20`）のまま扱い、年・月・日の数字で計算する。「今日」は日本時間で求める（`jstDateOf`）。月末・月初・0 時台の予約と、海外の時刻に設定したパソコンでテストする |
| 2 | **終わりの時刻が無い予約がある**（予約は開始時刻だけを持つ） | 所要時間は `customer_info` の合計時間 → メニューの所要時間 → 60 分、の順で決める（Google カレンダーの予定を作るときと同じ計算 = `buildEventParamsFromReservation` を使う） |
| 3 | 時刻の無い予約（第三希望日時のフォームで日付だけ決まっているもの） | 一番上の「時間未定」の欄に置く。ドラッグでは動かさない |
| 4 | 宿泊の予約（数日にまたがる） | 月表示は日をまたぐ帯、日・週表示は上の「終日」の欄。ドラッグでは動かさず、編集フォームで変える |
| 5 | **ドラッグで動かした先が埋まっている** | 落としたときに確認を出す（「11/25 14:00 に変更します。この時間には他の予約が 1 件あります」）。店舗の判断で重ねることはできる（電話で調整済みの場合があるため、止めはしない） |
| 6 | 動かしたのに保存に失敗した | 帯を元の位置に戻し、エラーを出す。保存中は同じ帯を動かせないようにする |
| 7 | 動かすとお客様に通知が飛ぶと思われる / 飛ばないと思われる | 確認の文に「お客様への通知は送られません」と明記する（管理画面からの変更は通知しない、という今の動きのまま） |
| 8 | 1000 件を超える月がある | 期間で絞って取得し、`fetchAllRows` を使う |
| 9 | キャンセル済みの予約が場所を取る | 既定は非表示。「キャンセルも表示」で薄く出す |
| 10 | スマホではドラッグが難しい | スマホは日表示を既定にし、移動は予約を開いて「日時を変更」から行う（ドラッグは PC だけ） |
| 11 | 2 人が同じ予約を同時に動かす | 保存時に、画面を開いたときの更新日時と比べる。変わっていたら「他の人が変更しました。読み込み直してください」 |
| 12 | Google カレンダーの取得に失敗した | 予約だけ表示し、上に「Google カレンダーの予定を読み込めませんでした」と出す（画面全体を止めない） |
| 13 | スタッフ選択の予約で、担当を変えたい | 3 本目（スタッフ列）で対応。それまでは編集フォームから変える |

### ②-3 で決めたこと

- **出すのは日表示だけ**: 週表示でスタッフごとに分けると列が多くなりすぎるため、日表示に「スタッフごとに表示」のチェックを置きます（既定 ON）。スタッフ選択を使っていない店舗では出ません
- **列は名前でまとめる**: スタッフはフォームごとに登録するので、同じ人でもフォームによって ID が違うことがあります。同じ名前は 1 つの列にまとめます
- **担当を変えられる相手**: その予約のフォームに登録されているスタッフだけです。別のフォームにしか居ないスタッフの列に落とすと、変えられない理由を出します
- **「担当なし」の列**: 担当の決まっていない予約がある日だけ出します。この列へは動かせません（担当を外すのは「予約内容を編集」から）
- **指名料**: 担当を変えても変えません（管理画面の予約編集と同じ）
- **スタッフの Google カレンダーの予定**: スタッフごとの列を開いたときだけ読みます（月・週表示では読まない = 通信を増やさない）。API はスタッフ名ごとに返し、カレンダー ID（メールアドレス）は返しません

### ②-2 で決めたこと

- **時刻の刻み**: 落とした位置は、フォームの時間間隔が 10 分・20 分なら 10 分、それ以外は 15 分に丸めます。時間間隔そのものにしなかったのは、45 分間隔の 9:45 や「追加で表示する分」の時刻にも合わせられるようにするためです
- **月表示でのドラッグ**: 別の日のマスに落とすと、時刻はそのままで日だけ変わります
- **空いている所からの手動予約**: 既存の店舗側手動予約フォームを、その日時を選んだ状態で新しいタブに開きます（カレンダーの中に入力フォームは作っていません）。フォームで受け付けていない時間なら、フォームの中で選び直します
- **同時に変更されたとき**: 保存のときに、画面を開いたときの更新日時（`expected_updated_at`）と比べ、変わっていたら保存しません

### ②-1 で設計から変えた点

- **表示設定の持ち方**: タブの ID `calendar` は「タブの一覧」（`admin_visible_tabs`）には入れず、項目の設定（`admin_visible_options.calendar`）で持ちます。設定画面では「予約管理」の下の「カレンダーを表示」です。タブの一覧に入れると、タブを絞り込んで保存している既存の店舗で「予約管理は出ているのにカレンダーだけ出ない」になるためです。未設定は予約管理に連動し、予約管理が非表示でもカレンダーだけ表示にできます（設計どおり）
- **宿泊の予約の月表示**: 日をまたぐ 1 本の帯ではなく、掛かっている日ごとに「宿泊」の札を出します
- **API の `staff_id`**: まだありません（スタッフごとの列を作る ②-3 で足します）。スタッフごとの Google カレンダーの予定も、まだ読みません
- **外部予約メール連携の予約**（ホットペッパーなど）: 予約としては出ず、Google カレンダーの予定として灰色の「予定あり」で出ます

### PR の分け方

| PR | 内容 | 確認すること |
|---|---|---|
| ②-1 | タブの追加、月 / 週 / 日の表示（自作）、予約を押すと詳細、キャンセルの表示切り替え、Google カレンダーの予定を灰色で表示 | 月末・月初・深夜の予約が正しい日に出る。宿泊・時間未定の予約が崩れない。予約管理を非表示にした店舗でカレンダーが出ない |
| ②-2 | ドラッグで移動（PC）、空いている所を押して手動予約 | 動かすと Google カレンダーの予定も動く。失敗すると元に戻る |
| ②-3 | スタッフごとの列表示、列をまたいで担当を変更 | スタッフ選択を使っていない店舗では出ない |

## 7. ③ リッチメニュー作成

### どんな機能か

**公式 LINE のトーク画面の下に出るメニュー（画像 + ボタン）を、管理画面で作って反映する機能**です。
公式 LINE の管理画面でも作れますが、このシステムで作ると次のことができます。

- 「予約確認」「予約を変更」「空き待ち確認」など、このシステムの機能を呼び出すボタンを選ぶだけで置ける
- **お客様ごとにメニューを切り替える**（新規とリピーターで変える、タグで変える）= 3 本目

### LINE の決まり（守らないと反映に失敗する）

| 項目 | 決まり |
|---|---|
| 画像の形式 | JPEG か PNG、1MB まで |
| 画像の大きさ | 幅 800〜2500px、高さ 250px 以上、横 ÷ 縦 が 1.45 以上。標準は 2500×1686（大）と 2500×843（小） |
| ボタンの数 | 1 枚に 20 個まで |
| メニューの数 | 公式 LINE 1 つにつき 1000 個まで |
| 変更 | **反映したメニューは書き換えられない**。変えるときは新しく作って差し替える |

※ 実装の前に、LINE の公式ドキュメントで最新の値を確認します。

### どのメニューが表示されるか（優先順位）

```
1. お客様ごとに設定したメニュー（このシステムから）
2. 全員向けのメニュー（このシステムから）
3. 公式 LINE の管理画面で設定したメニュー
```

このシステムで反映すると、公式 LINE の管理画面のメニューより優先されます。画面に「反映すると、公式 LINE の管理画面で設定したメニューの代わりにこちらが表示されます」と明記します。

### データ

`line_rich_menus`（新しい表）

| 列 | 内容 |
|---|---|
| `store_id` / `name` | 店舗 / 管理用の名前 |
| `size` | 大（2500×1686）/ 小（2500×843） |
| `image_url` | アップロードした画像 |
| `areas` | ボタンの範囲と動き（JSON） |
| `chat_bar_text` | メニューを開くバーの文言（14 文字まで） |
| `status` | 下書き / 反映中 / 反映に失敗 |
| `line_rich_menu_id` | LINE 側の ID（反映したとき） |
| `is_default` | 全員向けにしているか |
| `rule` | お客様ごとの切り替え条件（3 本目） |
| `last_error` | 失敗したときの理由 |

### ボタンの動き

| 種類 | 内容 |
|---|---|
| URL を開く | 予約フォーム（店舗のフォームから選ぶ）/ 任意の URL |
| 文字を送る | 「予約確認」「予約を変更」「空き待ち確認」「キャンセル」/ キーワード自動応答の言葉 / 任意の文字 |
| 別のメニューに切り替える | タブのように 2 枚を行き来する（2 本目以降） |
| 何もしない | 飾りの部分 |

「文字を送る」は、このシステムの予約語を一覧から選べるようにします（手で打つと 1 文字違いで反応しない）。

### 反映の流れ（順番が大事）

```
1. LINE に新しいメニューを作る          → 失敗したら何も変えずに終了
2. 画像をアップロードする               → 失敗したら 1 で作ったものを消して終了
3. 全員向けに設定する                   → 失敗したら 1 で作ったものを消して終了
4. このシステムの記録を「反映中」にする
5. 古いメニューを LINE から消す         → 失敗しても反映は成功扱い（あとで掃除）
```

**新しいメニューが表示される状態になってから、古いものを消します。**
先に消すと、途中で失敗したときにメニューが何も出ない時間ができます。

### 注意点（バグになりやすい所）

| # | 起きうること | 対策 |
|---|---|---|
| 1 | **差し替えの途中で失敗し、メニューが消える / 古いまま残る** | 上の順番を守る。各段階の結果を記録し、「反映に失敗」と理由を画面に出す。古いメニューの消し残りは次の反映のときに掃除する |
| 2 | 画像が大きすぎて LINE に断られる | サーバーで `sharp` を使い、決まった大きさに合わせて 1MB 以下に縮めてから送る。縦横比が合わない画像は、アップロードのときに切り抜き画面（既存の `ImageCropperModal`）を出す |
| 3 | **ボタンの位置がずれる**（画面では 400px 幅で編集し、実物は 2500px） | 範囲は「画像全体に対する割合」で持ち、送るときに実寸へ直す。端数は四捨五入し、画像からはみ出さないように丸める。計算は純粋ロジックにしてテストする |
| 4 | ボタンの範囲が重なっている | 保存のときに重なりを調べて止める |
| 5 | トークンが無効 / 権限が無い | 401・403 は「LINE のチャネルアクセストークンを確認してください」と出す |
| 6 | 反映ボタンを 2 回押して、メニューが 2 つできる | 押した直後に無効にする。記録を「反映の途中」にしてから LINE と通信する |
| 7 | このシステムの外（公式 LINE の管理画面や他のツール）でメニューを変えられた | 画面を開いたときに LINE の今の設定を読み、記録と違えば「他の場所で変更されています」と出す |
| 8 | メニューを使うのをやめたい | 「反映をやめる」ボタン（全員向けの設定を外す）。外すと公式 LINE の管理画面のメニューに戻ることを明記 |
| 9 | local では LINE と通信できない | local は記録だけ更新し、「local では LINE に反映しません」と出す |
| 10 | 予約フォームの URL を変えた / フォームを消した | ボタンは「フォームを選ぶ」形で持ち、反映のときに URL にする。消えたフォームを指すボタンがあれば警告 |
| 11 | メニューが 1000 個の上限に近づく | 古いメニューは差し替えのたびに消す。お客様ごとの切り替えは「条件ごとに 1 個」にして、人数ぶんは作らない |

### ③-1 で設計から変えた点・決めたこと

- **LINE の決まりは、公式ドキュメントで確認して上の表のとおりでした**（2026-11）。追加で分かったこと: 画像の送信だけ通信先が違う（`api-data.line.me`）/ 作ったメニューは画像の差し替えもできない / 全員向けの設定を読むと、設定が無いときは 404、ほかの場所で設定されているときは 403 が返る
- **画像の加工はブラウザで行います**（サーバーに画像の加工の道具を足さないため）。画像を選ぶ → メニューの形に切り抜く → その大きさの JPEG にして 1MB 以下に縮める、までを画面の中で行い、サーバーは反映のときに大きさを確かめるだけです
- **表示設定は既定で非表示にしました**。公式 LINE の全員向けメニューを差し替える機能なので、「店舗管理者に表示するメニュー」でチェックを入れた店舗の店舗管理者だけに出します。運営（テナント側の店舗ページ）からは、いつでも使えます
- **消し残りの掃除**: このシステムが LINE に作るメニューは、名前の先頭に印（`[nas-rsv] `）を付けます。次の反映のとき、その印の付いた古いメニューだけを消します
- **未反映の変更**: 反映中のメニューを編集して保存すると「未反映の変更あり」と出します。「もう一度反映する」を押すまで、公式 LINE には古い内容が出ています
- ボタンの動きの「別のメニューに切り替える」は ③-2 で作ります。表の `rule` 列は ③-3 用に先に作ってあります（いまは使いません）

### ③-3 で決めたこと

- **条件の持ち方**: メニューに「だれに出すか」の条件（配信の「配信先の条件」と同じ形）を付けます。条件ごとにメニューを 1 個作り、LINE には「この人にはこのメニュー」と 500 人ずつまとめて設定します。出せるのは 5 個までです
- **優先順位**: 条件が重なるお客様には、一覧で上にある（優先の数字が小さい）メニューが出ます。一覧の矢印で入れ替えます
- **いつ見直すか**: メニューを出す・やめる・優先順位を変えるとき / 予約が入ったとき / 顧客情報（タグなど）を変えたとき / 1 日 1 回（本番だけ cron を登録）/ 画面の「いま見直す」。アンケートの選択肢タグや LINE の分岐で付いたタグは、1 日 1 回の見直しで拾います（その場では見直しません）
- **設定を外すのは、このシステムが設定した人だけ**です。だれに設定したかを記録しておき（`line_rich_menu_links`）、条件に合わなくなった人だけを外します
- **配信停止のお客様にも出します**（メニューは配信ではないため）。ブロックされているお客様・LINE と連携していないお客様は対象外です
- **タブ切り替えとは一緒に使えません**。どちらも「お客様 1 人ずつにメニューを付ける」仕組みなので、お客様ごとのメニューには切り替えのボタンを置けず、切り替え先にもできません
- **全員向けのメニューとは独立**しています。全員向けの「反映する」「反映をやめる」を押しても、お客様ごとのメニューは出したままです
- **チャネルシークレットを登録した店舗だけ**で使えます（設計どおり）。未登録の店舗では、条件を付けて保存はできますが、出すことはできません

### ③-2 で決めたこと

- **型**: 公式 LINE の管理画面にある型と同じ並びを用意しました（大 = 6 分割・4 分割・上 1 + 下 3・上 1 + 下 2・左大 + 右 2・上下 2、小 = 3 分割・左 1/3 + 右 2/3・左 2/3 + 右 1/3、共通 = 2 分割・全体）。型を選ぶと、いまのボタンの動きを上から順に引き継ぎます
- **タブ切り替えの仕組み**: LINE の決まりで、切り替え先のメニューに「名札」（エイリアス）を付け、ボタンにその名札を書きます。名札は画像を入れたメニューにしか付けられないので、切り替えでつながっているメニュー（5 個まで）は**まとめて**反映します。全員向けになるのは、「反映する」を押したメニューだけです
- **名札は反映のたびに新しくします**。古い名札を書き換えないので、途中で失敗しても、いま出ているメニューの切り替えは壊れません。古い名札とメニューは、新しいものが出たあとに消します
- **切り替え先のメニュー**は、一覧で「切り替え先として反映中」と出します。切り替え先だけの「反映をやめる」はできません（元のメニューの反映をやめると、一緒に下書きに戻ります）
- **プレビュー**: 編集画面の右側を「スマホでの見え方」に切り替えます。近似の表示です
- **実機で確かめること**: お客様が切り替え先のメニューを見ている最中に反映し直したとき、そのお客様のメニューがどう見えるか（LINE の文書に書かれていないため。全員向けのメニューに戻る想定）

### お客様ごとの切り替え（3 本目）

- 条件: 新規（予約 0〜1 回）/ リピーター / タグあり、など。配信の「配信先の条件」と同じ部品（`matchAudience`）を使います
- いつ切り替えるか: 予約が入ったとき・タグが変わったとき・1 日 1 回の見直し
- LINE への設定は 500 人ずつまとめて送ります
- 条件に合わなくなった人は、設定を外して全員向けに戻します
- **[4 章](#4-先に直しておくことwebhook-の署名チェック)の署名チェックが済んだ店舗だけで使えるようにします**
- 注意: 条件が重なる人がどちらになるかを、優先順位（上にある条件が勝つ）で決めて画面に出します

### PR の分け方

| PR | 内容 | 確認すること |
|---|---|---|
| ③-1 | 表、画像のアップロードと切り抜き、ボタンの範囲と動きの編集、反映 / 反映をやめる | 本番のデモ店舗で、反映 → 実機にメニューが出る → ボタンが正しい位置で動く → 差し替えても途切れない |
| ③-2 | 分割の型（2 分割・3 分割・6 分割など）、スマホ枠のプレビュー、タブ切り替え | 型を選ぶだけで範囲が入る |
| ③-3 | お客様ごとの切り替え | 条件に合う人だけメニューが変わり、外れると戻る |

## 8. ④ 1対1トーク

### どんな機能か

**お客様が公式 LINE に送ったメッセージを管理画面で読み、そこから返信できる機能**です。
顧客の情報（予約・来店・メモ）を見ながら返信できるのが、公式 LINE の管理画面のチャットとの違いです。

### 使えるようにする条件（重要）

**既定は OFF。弊社が店舗ごとに ON にしない限り、何も保存しません。**

| 設定 | 誰が変えられるか | 既定 |
|---|---|---|
| トーク機能を使う（`chat_enabled`） | **マスター管理者・システム管理者だけ**（テナント側の店舗ページ） | OFF |
| 会話の保存期間（1 年 / 2 年 / 3 年） | マスター管理者・システム管理者 | 1 年 |
| スタッフの LINE に通知する | 店舗管理者も変えられる | OFF |
| メールで通知する（宛先） | 店舗管理者も変えられる | OFF |
| 管理画面の未読バッジ | —（常に出る） | — |

- ON / OFF と保存期間は、**API 側で役割を確認します**（画面で隠すだけだと、店舗管理者が直接 API を呼んで ON にできてしまう）
- ON にできるのは、Webhook の署名チェック（[4 章](#4-先に直しておくことwebhook-の署名チェック)）が済んだ店舗だけです
- OFF の店舗では、Webhook は会話を保存せず、タブも出しません
- ON → OFF にしたとき: 新しい会話は保存しなくなります。保存済みの会話は消さず、保存期間が過ぎたら自動で消えます（すぐ消したい場合は「会話をすべて削除」を弊社だけが押せる）

### データ

`chat_threads`（お客様 1 人との会話 1 本）

| 列 | 内容 |
|---|---|
| `store_id` / `line_user_id` | 店舗 / LINE ユーザー（この 2 つで 1 本。重複不可） |
| `customer_id` | 顧客（見つかれば。無ければ null） |
| `last_message_at` / `last_message_preview` | 一覧の並び順と 1 行表示 |
| `unread_count` | 未読の数 |
| `status` | 対応中 / 対応済み |
| `notified_at` | 最後に通知を送った日時（通知の送りすぎ防止） |

`chat_messages`（メッセージ 1 通）

| 列 | 内容 |
|---|---|
| `thread_id` / `store_id` | 会話 / 店舗 |
| `direction` | お客様から / 店舗から / システム（自動の記録） |
| `kind` | 文字 / 画像 / スタンプ / その他 |
| `text` / `media_path` | 本文 / 画像の保存場所 |
| `auto` | フォームが自動で送った文（予約内容など）かどうか |
| `line_message_id` | LINE 側の ID（**重複不可** = 二重保存の防止） |
| `client_key` | 送信ボタンを押したときに画面が作る ID（**重複不可** = 二重送信の防止） |
| `send_status` | 送信中 / 送信済み / 失敗（理由つき） |
| `sent_by` | 返信したスタッフ |
| `created_at` | LINE の通知に入っている日時（届いた順ではなく、送られた順に並べるため） |

- 権限: どちらの表も RLS のポリシーを付けません（サーバー側の鍵でしか読めない）。画面からは必ず API を通します
- 会話は **LINE ユーザー ID で 1 本**にします。顧客の表は同じ人が 2 人登録されていることがあり（2026-11-20 のデモ店舗の調査）、顧客 ID でまとめると会話が分かれてしまうためです

### 受け取る流れ

```
お客様が公式 LINE に送る
  → LINE から Webhook に通知
  → 署名を確認（偽の通知を捨てる）
  → トーク機能が ON の店舗なら、会話に保存（同じ line_message_id は 1 回だけ）
  → 既存の処理（予約確認・キーワード応答など）はこれまでどおり動く
  → LINE に応答を返す
  → そのあとで: 画像の取得と縮小 / 未読の加算 / 通知
```

**保存するもの・しないもの**

| 届くもの | 扱い |
|---|---|
| 文字 | 保存 |
| 画像 | 縮めて保存（長辺 1600px の JPEG） |
| スタンプ | 「スタンプ」と表示（LINE のスタンプ画像の URL が分かるものは画像で） |
| 動画・音声・ファイル・位置情報 | 「動画が送られました」のように種類だけ表示し、中身は保存しない（決定）。中身は公式 LINE のアプリで見てもらう旨を画面に出す |
| グループ・複数人トークからの通知 | 保存しない（1対1 だけ） |
| **フォームが自動で送る文**（【予約フォーム】…、【空き待ち登録】…、【メニュー変更】… など） | 保存するが `auto` の印を付け、**未読に数えず、通知もしない** |
| **コマンド**（「予約確認」「予約を変更」「キャンセル: 3」「配信停止」など） | 同じく `auto` |

`auto` の印を付けないと、予約が入るたびに「新着メッセージ」の通知が飛び、未読が増え続けます。
判定は純粋ロジック（`isAutoMessage(text, 店舗の予約語)`）にまとめ、既存の予約語の一覧（`RESERVED_KEYWORDS` / `SYSTEM_KEYWORDS` / 各機能の見出し文字）から作ります。

### 返信する流れ

```
スタッフが文字を入れて送信
  → 画面が client_key（1 回の送信に 1 つの ID）を作る
  → サーバーが「送信中」で保存（同じ client_key は 1 回だけ）
  → LINE に push で送る（X-Line-Retry-Key = client_key）
  → 成功: 送信済み / 失敗: 失敗（理由を保存）
```

- 返信は **push（通数を使う送り方）** にします。無料で返せる方法（reply）は、お客様の発言から約 1 分以内しか使えず、既存の自動応答が先に使うことも多いので、第 1 弾では使いません
- 入力欄の近くに「返信 1 通につき、公式 LINE の通数を 1 通使います」と、今月の残り通数（配信タブと同じ `fetchLineQuota`）を出します
- 月間の上限に達していると送れません。LINE の返答を見て「今月の通数の上限に達しています」と出します
- ブロックされているお客様には届きません。失敗の理由を「ブロックされているため届きませんでした」と出します
- 画像の返信: LINE に渡す画像は、外から見える https の URL が必要です。推測できない名前で公開の場所に置きます（メニュー画像と同じ方式）。お客様から届いた画像は公開しません

### 自動で送ったメッセージを会話に出す（決定: 最初から出す）

リマインダーや配信など、このシステムが自動で送ったメッセージも会話に並べます。スタッフが「いつ何が届いているか」を見ながら返信できます。

**出すもの**

| 送るもの | 送っている場所 | 会話での表示 |
|---|---|---|
| 予約リマインダー（前日・当日・直前） | Edge Function `send-reminders` | 「リマインダーを送信しました（11/25 14:00 のご予約）」 |
| フォローメッセージ | Edge Function `send-follow-messages` | 「フォローメッセージを送信しました」 |
| 配信・自動配信 | Edge Function `send-broadcasts` | 「配信『〇〇』を送信しました」 |
| 予約確認・キャンセル・予約変更などの自動応答 | Webhook | 「【ご予約確認】を返信しました」 |
| キーワード自動応答・あいさつメッセージ | Webhook | 「『〇〇』を返信しました」 |
| 空き待ちのお知らせ・おわび | `waitlist-service` | 「空きのお知らせを送信しました」 |

**作り方**

- 送った本文そのものではなく、**「何を送ったか」の 1 行**を、システムの記録（`direction = システム`）として会話に足します。カードの中身まで保存すると、データ量が大きくなり、配信の内容と二重に持つことになるためです
- 記録する関数は 1 つ（`recordChatSystemEvent(storeId, lineUserId, 種類, 説明, 送った日時)`）にまとめ、送っている各場所から呼びます
- **トークが ON の店舗だけ記録します**（OFF の店舗では何もしない）

**注意点**

| # | 起きうること | 対策 |
|---|---|---|
| a | **記録に失敗して、リマインダーや配信が止まる** | 記録は送信が終わったあとに行い、失敗しても送信の結果は変えない（ログに残すだけ） |
| b | 同じ送信が 2 回記録される（送信処理の再試行） | 記録に「元の送信の ID」（リマインダーの送信記録 ID・配信の宛先 ID など）を持たせ、重複不可にする |
| c | 配信で数千人に送ると、記録を 1 行ずつ書いて遅くなる | 配信は宛先をまとめて書き込む（500 行ずつ） |
| d | Edge Function（Deno）は Next.js 側の関数を呼べない | Edge Function からは DB の関数 `chat_record_system_event` を呼ぶ。Next.js 側も同じ関数を使い、書き込む形を 1 か所にまとめる |
| e | 自動の記録で未読が増える・通知が飛ぶ | システムの記録は未読に数えず、通知もしない |
| f | 手を入れる場所が多い（送信処理 6 か所 + Edge Function 3 本の再デプロイ） | 1 つの PR（④-5）にまとめ、**送信そのものの動きは変えない**。リリースのときに Edge Function 3 本を再デプロイする |

### 利用量の記録（決定: 有料オプションにする）

料金を決める・請求するときの材料として、店舗ごとの利用量を数えます。

- 数えるもの: 月ごとの 受信数 / 返信数 / 保存している画像の容量 / ON にした日
- 保存: 毎回数え直すと重いので、`chat_usage_monthly`（店舗 × 月で 1 行）に足していきます。足すのは DB の関数で行います（同時に届いても数がずれないように）
- 画面: マスター管理者のページに「トークの利用状況」（店舗ごとの今月・先月の数）。CSV でダウンロードできるようにします
- 自動で送ったメッセージの記録と、フォームの自動文（`auto`）は、返信数・受信数に数えません（店舗が使ったぶんだけを数える）
- **料金の計算や請求そのものは作りません**（数を見せるところまで）。金額と請求の方法が決まったら、別に設計します

### 画面

- 新しいタブ「トーク」（`chat`。ON の店舗だけ出る。店舗管理者に表示するメニューでも出し分け可）
- 左: 会話の一覧（未読が上、新しい順。名前で検索、未読だけ / 対応中だけの絞り込み）
- 中: 会話（吹き出し。お客様は左、店舗は右。`auto` は小さく薄く表示）
- 右: 顧客の情報（予約・タグ・メモ。顧客詳細へのリンク）。顧客が見つからない人は LINE の表示名だけ
- スマホ: 一覧 → 会話 の 2 画面
- 顧客詳細の LINE タブに「トークを開く」

### 未読と通知

**未読バッジ（常に出る）**

- タブに未読の合計を出します
- 確認は 15 秒おき・タブが見えているときだけ・新着が無い間は 30 秒まで延ばす（2 章の「④ で気をつける数字」）
- 会話を開いたら既読にします（未読の数を 0 に）
- 未読の加算は DB の関数で行います（読んでから 1 足して書く、だと同時に届いたときに数がずれる）

**スタッフの LINE に通知（任意）**

- 朝のまとめで使っている「スタッフ登録」の仕組み（`store_digest_staff`）で登録したスタッフに送ります
- **公式 LINE の通数を使います**（1 回 × スタッフの人数）。設定画面に明記します
- 送りすぎの防止: 同じ会話については、未読が続いている間は 10 分に 1 回まで

**メールで通知（任意）**

- 宛先は 5 件まで。送信は既存の Resend（`sendEmail`）
- 同じ会話については 10 分に 1 回まで
- **メールには本文を載せません**（「〇〇様から新しいメッセージが届きました」とリンクだけ）。メールは転送されたり、他の人の目に触れたりするためです

### 自動削除（保存期間）

- 1 日 1 回、保存期間（1 年 / 2 年 / 3 年）を過ぎたメッセージを消します
- 順番: 画像の場所を集める → 画像を消す → メッセージの行を消す → 空になった会話を消す
  （行を先に消すと、画像の場所が分からなくなって画像だけ残る）
- 1 回に消す量に上限（例: 5000 行）を付け、残りは次の日に回します
- 起動は pg_cron `run_chat_retention`（1 日 1 回。**本番だけ登録**）→ `POST /api/cron/chat-retention`
- 保存期間を 3 年 → 1 年に変えると、次の実行で 1 年より古い会話が消えます。変更のときに「1 年より前の会話は削除されます」と確認を出します

### 注意点（バグになりやすい所）

| # | 起きうること | 対策 |
|---|---|---|
| 1 | **偽のメッセージが表示される** | Webhook の署名チェックが済んだ店舗でしか ON にできない |
| 2 | **同じメッセージが 2 回保存される**（LINE は応答が遅いと送り直す） | `line_message_id` を重複不可にし、重複は黙って捨てる |
| 3 | **返信が 2 回送られる**（連打・通信の再試行） | `client_key` を重複不可にし、LINE への送信にも同じ鍵を付ける。ボタンは押した直後に無効 |
| 4 | **他の店舗の会話が見える** | すべての API で `authorizeStoreAccess`。会話 ID だけで読ませず、必ず店舗 ID と一緒に確認する。テストで「他店舗の会話 ID を指定すると 404」を確かめる |
| 5 | **予約のたびに通知が飛ぶ** | フォームの自動文・コマンドに `auto` を付け、未読と通知の対象から外す |
| 6 | 送ったのに「送信中」のまま | LINE との通信に 10 秒の制限時間。超えたら「失敗」にして再送ボタンを出す（同じ `client_key` で再送するので二重にならない） |
| 7 | メッセージの順番が入れ替わる | LINE の通知に入っている日時で並べる。同じ時刻は ID の順 |
| 8 | 画像の取得に失敗する（LINE 側の保存期間切れ・通信エラー） | メッセージは「画像（読み込めませんでした）」として残す。取得は 3 回まで再試行 |
| 9 | 画像でデータが増えすぎる | 縮めて保存。1 枚の上限 10MB（超えたら保存しない） |
| 10 | 本文に入れられた記号で画面が壊れる / 危険なリンク | 本文は文字としてだけ表示（HTML として解釈しない）。リンクにするのは `http` / `https` だけ |
| 11 | 公式 LINE の管理画面のチャットから返信した内容が、こちらに出ない | **LINE の仕様で、店舗側が送った内容は通知されません。** 併用すると会話が片側だけになるので、「トーク機能を使う店舗は、返信をこの画面に統一してください」と ON にするときに案内する |
| 12 | 自動で送った内容の記録に失敗して、リマインダーや配信そのものが止まる | 記録は「送信が終わったあと」に行い、失敗しても送信は成功扱いにする（「自動で送ったメッセージを会話に出す」の節） |
| 13 | 2 人のスタッフが同時に返信する | 返信した人の名前を吹き出しに出す。送信の前に最新の会話を読み直す |

### 個人情報について（作る前に必ず確認）

会話には、体の悩み・病歴・家族のことなど、**特に慎重に扱うべき内容が入ることがあります**。

- プライバシーポリシー（`/privacy`）と利用規約（`/terms`）に、「公式 LINE のトーク内容を保存し、店舗が閲覧する」ことを追記します
- 店舗側にも、お客様への説明（公式 LINE のあいさつ文やプロフィールへの記載）をお願いする必要があります
- 保存期間を過ぎたら必ず消えること、弊社が ON にした店舗だけで保存されることを、店舗への案内に書きます
- **追記する文の下書きは、④-1 を作るときにこちらで用意します**（決定）。弊社で内容を確認してから公開します。法律上の最終判断は弊社（必要なら専門家）で行います

### ④-4 で決めたこと・設計から変えた点

| 項目 | 決めたこと |
|---|---|
| 届いた画像を縮めるか | **縮めずに、そのまま保存する**（設計では「長辺 1600px の JPEG に縮める」）。サーバーに画像を加工する部品（`sharp`）が入っておらず、足すと Vercel のビルドと関数の大きさに影響するため。10MB を超える画像は保存しない。LINE のアプリは、送るときに画像を縮めるので（標準の画質で 1〜2MB 前後）、実際に大きな画像が届くことは少ない。保存の量が問題になったら、縮める処理を足す |
| 届いた画像の置き場 | 公開しないバケツ `chat-media`。画面には、ログインと店舗を確かめる API を通して出す（公開の URL も、期限つきの URL も作らない） |
| 画像を取りにいくタイミング | 保存と通知のあと（LINE への応答を返したあと）。3 回まで試す。取れなかった画像は、あとから取り直せない（LINE 側に残っていないため）ので「読み込めませんでした」と出す |
| 店舗が送る画像 | 画面で縮める（長いほうの辺 1600px・1MB 以下の JPEG）。公開の置き場に、推測できない 32 桁の名前で置く。**返信の API は、その店舗の置き場の画像の URL だけを受け付ける** |
| 送らなかった画像 | アップロードしただけで送らなかった画像は、置き場に残る（消す処理は作っていない） |
| 定型文の保存先 | `chat_settings.reply_templates`（別の表にはしていない）。店舗ごと・30 個まで。店舗管理者も変えられる |
| 対応済み | 手で切り替える。お客様から自動でない新しいメッセージが届くと、対応中に戻る。返信しただけでは変わらない |
| 検索 | 名前での検索（④-2 で実装済み）に、「対応中」の絞り込みを足した。メッセージの本文の検索は作っていない |
| 自動削除と画像 | 画像のファイルを消してから行を消す（④-3 で残していた宿題）。画像を消せなかったメッセージは、行を残して次の日にもう一度試す |
| 顧客を削除するとき | 確認に「トークの会話は残ります」と出す。会話を一緒に消す選択肢は付けていない（会話を消す操作そのものが、まだ無い） |
| 実機で確かめていないこと | LINE から画像を取得するところ・公開しないバケツへの保存と読み出し・LINE への画像の送信。local は LINE と通信せず、Supabase の Storage も使わないため。本番のテスト用店舗で確かめる |
