# 顧客管理（β）カルテ機能 提案書

作成日: 2026-09-04 / 対象: 店舗管理者ページ「顧客管理」の顧客詳細を、来店のたびに使う「カルテ」に育てるための機能提案

---

## 1. この資料について

顧客管理タブでは顧客一覧と詳細（基本情報・統計・予約履歴・来店履歴・抽選履歴・LINE 情報）が見られますが、**施術の内容や次回への申し送りを残す場所が「メモ」1 つしかなく**、美容室・ネイル・エステ・整体などの業態で日常的に使う「カルテ」としては足りません。

この資料では、**すでにデータベースにあって画面に出ていない項目**を最優先で活かしつつ、来店前の確認 → 施術中の記録 → 次回の提案、までを 1 画面で回せるカルテ機能を提案します。

各案には次を付けています。

- **店舗の使い方**: いつ・誰が・何のために使うか
- **流用度**: 既存の仕組みをどれだけ使い回せるか（★が多いほど早く作れる）
- **工数の目安**: 抽選フォーム（全 5 Phase）を 100 としたときの相対値
- **注意点**: 個人情報・運用上のリスク

## 2. 現状の整理（何があって、何が無いか）

### 2-1. すでに DB にあるのに画面に出ていない項目（最初に活かすべき資産）

| テーブル | 列 | 用途 | 画面での扱い |
|---|---|---|---|
| `customers` | `allergies` | アレルギー | **未表示・未編集** |
| `customers` | `medical_history` | 既往歴・注意事項 | **未表示・未編集** |
| `customers` | `tags` | タグ（配列） | **未表示・未編集** |
| `customers` | `preferred_contact_method` | 希望連絡手段 | **未表示・未編集** |
| `customer_visits` | `treatment_notes` | 施術メモ | **未表示** |
| `customer_visits` | `therapist_name` | 担当者 | **未表示** |
| `customer_visits` | `satisfaction_score` | 満足度（1〜5） | **未表示** |
| `customer_visits` | `payment_method` | 支払い方法 | **未表示** |
| `customer_interactions` | テーブル全体 | 電話・メール・LINE・メモなどの対応履歴 | **UI から一切使われていない** |

つまり、**テーブルを 1 つも増やさなくても「カルテの半分」は作れます**。これが案 1 と案 2 の根拠です。

### 2-2. 既存の仕組みで流用できるもの

| 仕組み | 中身 | 使う案 |
|---|---|---|
| 顧客詳細の全画面シート（`MobileSheet`）・チップタブ・統計タイル | スマホ最適化済みの顧客詳細の骨格。タブを増やすだけでカルテを足せる | 全案 |
| 来店履歴（`customer_visits`）と統計の再計算 | 来店を記録すると来店回数・総利用額・平均来店間隔が自動更新 | 案 2・4 |
| 予約データ（メニュー・オプション・担当スタッフ） | 施術記録の下書きを予約から自動生成できる | 案 2 |
| 画像アップロード API（`/api/upload/menu-image`） | Supabase Storage への画像保存。カルテ写真に転用できる | 案 3 |
| リマインダーの定期実行（Edge Function） | 「そろそろ次回」の自動通知に転用 | 案 6 |
| 表示制御（`admin_visible_options`） | 店舗ごとにカルテ項目を出す / 出さない | 全案 |

### 2-3. 無いもの（新規に必要）

- 写真を保存するテーブル（案 3）
- カルテの項目を店舗ごとに定義する「テンプレート」（案 5）
- 施術記録を LIFF でお客様に見せる画面（案 7。`docs/LIFFフォーム企画案` の案 12 と同じ）

## 4. 各案の詳細

### 案 1: 注意事項・アレルギー・タグを顧客詳細の一番上に ◎（最初に）

**店舗の使い方**
- 来店前の確認、施術前の最終確認で、**顧客詳細を開いた瞬間に**アレルギー・既往歴・注意事項が目に入る
- タグ（「猫アレルギー」「妊娠中」「指名: 田中」「クレーム対応中」など）で一覧からも見分けられる

**画面（顧客詳細の基本情報の直下）**

```
┌──────────────────────────────┐
│ ⚠ アレルギー: ジアミン、ラテックス   │  ← 赤系の帯。未登録なら「登録なし」を薄く表示
│ ⚠ 既往歴・注意: 頭皮が敏感。刺激弱で │
│ 🏷 妊娠中  指名:田中  平日希望        │  ← タグ（タップで一覧の絞り込みへ）
│ 📞 希望連絡: LINE                   │
└──────────────────────────────┘
```

**設定できること**
- 編集フォームに「アレルギー」「既往歴・注意事項」「タグ」「希望連絡手段（LINE / 電話 / メール / 連絡不要）」を追加
- タグは店舗ごとの候補（よく使うタグ）から選ぶ + 自由入力
- 一覧の顧客カードにタグを 2 つまで表示。検索 API の `search` にタグを含める

**流用度: ★★★★★ / 工数: 15**
- DB の列はすべて既存。顧客 API（PATCH）はすでに任意の列を受け付ける
- `CustomerForm` に項目を追加、`CustomerDetail` に帯を追加、一覧の検索にタグを含めるだけ

**注意点**
- アレルギー・既往歴は個人情報保護法の**要配慮個人情報**にあたる可能性がある。「本人の同意を得て記録する」旨を編集フォームに明記し、プライバシーポリシーに「施術の安全のために健康に関する情報を記録する」ことを追記する
- CSV 出力にこれらを含めるかは店舗設定で選べるようにする（既定は含めない）

### 案 2: 施術記録（来店カルテ）の入力と一覧 ◎

**店舗の使い方**
- 施術後（または会計時）に、その来店の「何をしたか」を残す。次回来店時に前回の記録を見ながら施術する
- 予約から来店を記録するときに、**メニュー・オプション・担当スタッフ・金額が下書きとして自動で入る**ので、店舗は薬剤とメモを足すだけ

**画面（顧客詳細の「来店」タブを拡張）**

```
┌──────────────────────────────┐
│ 来店 (12)          [＋ 来店を記録] │
│ ┌──────────────────────────┐ │
│ │ 9/1（月）10:00  担当: 田中   │ │
│ │ カット＆カラー ¥12,000      │ │
│ │ 薬剤: イルミナ 8NB 20 分     │ │  ← 施術メモ（テンプレート項目 or 自由記述）
│ │ 満足度 ★★★★☆  支払: カード  │ │
│ │ 次回: トリートメントを提案   │ │  ← 申し送り（案 4）
│ │ [写真 2 枚]                  │ │  ← 案 3
│ └──────────────────────────┘ │
│ ┌──────────────────────────┐ │
│ │ 8/3（日） ...              │ │
└──────────────────────────────┘
```

**入力画面（全画面シート。スマホでレジ横でも入力できる）**
- 来店日時（予約から自動）/ メニュー（予約から自動。複数選択可）/ 担当（予約のスタッフ or 選択）/ 金額（メニュー価格から自動計算。手修正可）/ 支払い方法 / 施術メモ（自由記述。テンプレート項目は案 5）/ 満足度 / 次回への申し送り（案 4）
- 予約一覧・予約詳細からも「この予約の来店を記録」で開ける（予約ステータスを「完了」にするときに一緒に記録する導線）

**流用度: ★★★★☆ / 工数: 45**
- `customer_visits` の列（`treatment_menus` / `treatment_notes` / `therapist_name` / `satisfaction_score` / `amount` / `payment_method`）はすべて既存。統計の再計算も既存
- 新規は「来店記録の入力シート」「予約からの下書き生成」「来店タブの表示拡張」。API は `POST /api/stores/{storeId}/customers/{customerId}/visits` と `PATCH/DELETE .../visits/{visitId}` を追加

**注意点**
- 予約完了時に来店記録を自動作成している経路（既存）と二重にならないよう、「予約に紐づく来店記録があれば編集、無ければ新規」にする
- 金額を変えると総利用額と VIP 判定が変わる。編集時に「統計に反映されます」と注記する

### 案 3: カルテ写真（ビフォー / アフター） ◎

**店舗の使い方**
- 施術前後の写真、ネイルのデザイン、ヘアカラーの仕上がりを来店記録に添付する
- 次回来店時に「前回と同じ」「前回より明るく」を写真で共有できる

**画面**
- 来店記録の入力シートに「写真を追加」（カメラ起動 / ライブラリ）。1 来店あたり最大 6 枚、種類（ビフォー / アフター / 参考）を付けられる
- 顧客詳細に「写真」タブ（来店日ごとのギャラリー）。タップで拡大、左右スワイプ

**データ構造（新規）**

```sql
CREATE TABLE customer_photos (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  customer_id TEXT NOT NULL REFERENCES customers(id) ON DELETE CASCADE,
  store_id TEXT NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  visit_id TEXT REFERENCES customer_visits(id) ON DELETE SET NULL,
  kind TEXT NOT NULL DEFAULT 'after' CHECK (kind IN ('before', 'after', 'reference')),
  storage_path TEXT NOT NULL,        -- Supabase Storage（非公開バケット）
  caption TEXT,
  taken_at TIMESTAMPTZ DEFAULT now(),
  created_by UUID,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

**流用度: ★★★☆☆ / 工数: 40**
- 画像アップロードの仕組み（Storage）は流用。ただし**顧客写真は公開バケットに置いてはいけない**ため、非公開バケット + 署名付き URL（有効期限付き）で配信する部分が新規
- スマホでの撮影は `<input type="file" accept="image/*" capture="environment">` で OK。アップロード前に長辺 1600px に縮小して容量を抑える

**注意点**
- 顔写真は個人情報。**保存前に本人の同意**を得る運用にし、同意の記録欄（チェック + 日付）を来店記録に持つ
- 保存容量は店舗ごとに上限（例: 2 GB）を設け、テナント管理画面で使用量を表示する（提供側の原価管理。第 7 章の収益化案とも接続）
- 削除は物理削除（Storage からも消す）

### 案 4: 次回への申し送りと「次回提案」 ◎

**店舗の使い方**
- 施術後に「次回はトリートメントを提案」「前髪は切りすぎない」を 1 行残す
- 次回来店時（次の予約が入った時点、または顧客詳細を開いた時点）に、**顧客詳細の最上部に「前回の申し送り」として表示**。確認したら「確認済み」で消える
- 予約フォームの「前回と同じ」再予約や、リマインダーへの提案文の差し込み（`docs/LIFFフォーム企画案` の案 9・11・12）に、この申し送りをそのまま使える

**画面**

```
┌──────────────────────────────┐
│ 📝 前回の申し送り（9/1 田中）      │  ← 黄色の帯。最上部
│ 次回はトリートメントを提案。       │
│ 前髪は切りすぎない。   [確認済み]  │
└──────────────────────────────┘
```

**データ構造**
- `customer_visits.next_visit_note TEXT` と `next_visit_note_acknowledged_at TIMESTAMPTZ` を追加（1 来店に 1 つ。最新の未確認分だけを帯に出す）
- 「次回おすすめメニュー」は `next_visit_menu_ids TEXT[]` で予約フォームのメニュー ID を持ち、再予約や提案の自動化に使う

**流用度: ★★★★☆ / 工数: 25**

### 案 5: 店舗ごとのカルテ項目テンプレート ○

**店舗の使い方**
- 業態ごとに「毎回書く項目」が違う。自由記述だけだと書き忘れと表記ゆれが起きるので、店舗が入力欄を定義できるようにする

| 業態 | 項目の例 |
|---|---|
| 美容室 | 薬剤（メーカー・番号）/ 放置時間 / 施術部位 / 使用トリートメント / 仕上がりの長さ |
| ネイル | デザイン（写真）/ オフの有無 / ジェルの種類 / 長さ・形 / 持ち（前回からの日数） |
| エステ | 主訴 / 施術部位 / 使用機器 / 出力 / 肌の状態（乾燥・赤み）|
| 整体・治療院 | 主訴 / 痛みの部位・程度（1〜10）/ 施術内容 / 経過 |

**設計**
- テナント側 店舗設定に「カルテ項目」エディタ（アンケートの質問エディタを再利用: テキスト / 数値 / 選択 / 複数選択 / 日付 / 評価 1〜5）
- 業態別のプリセット（上の 4 種）を用意し、選ぶだけで使い始められる
- 来店記録の入力シートは、テンプレートの項目を上に、自由記述を下に表示
- 保存は `customer_visits.chart_data JSONB`（項目 ID → 値）。テンプレートを後から変えても過去の記録は当時の項目名で表示できるよう、項目名も一緒に保存する

**流用度: ★★★☆☆ / 工数: 50**

### 案 6: 対応履歴のタイムライン ○

**店舗の使い方**
- 「先週電話で相談があった」「LINE でキャンセルの連絡」「来店時にクレーム」を残し、予約・来店・施術記録と**同じ時系列**で見る
- 誰が対応したかが分かるので、スタッフ間の引き継ぎに使える

**画面**
- 顧客詳細に「タイムライン」タブ。予約 / 来店 / 施術記録 / 対応 / 抽選を 1 本に並べ、種類でフィルタ
- 「＋ 対応を記録」: 種類（電話 / メール / LINE / 来店時の会話 / メモ）、方向（受信 / 発信）、内容、担当

**流用度: ★★★★☆ / 工数: 35**
- `customer_interactions` テーブルが**そのまま使える**（列: 種類・方向・件名・内容・担当）。API と UI が新規
- リマインダー送信や抽選の当選通知を自動で `interaction_type = 'reminder' / 'line_message'` として記録すると、店舗が送った通知も同じ流れで見える

### 案 7: お客様への施術記録の共有（LIFF） ○（案 2・3 の後）

**店舗の使い方**
- お客様が LINE から「マイカルテ」を開き、前回の仕上がり写真・施術内容・次回のおすすめを見られる
- 「そろそろ次回の時期」の通知に前回の写真と申し送りを添えて送る

**設計**
- お客様に見せる項目は店舗が選ぶ（写真 / メニュー / 担当 / 次回提案。薬剤や内部メモは見せない）
- LIFF の本人確認（抽選フォームと同じ ID トークン検証）で、本人の記録だけを返す
- 写真は署名付き URL（短い有効期限）で配信

**流用度: ★★★☆☆ / 工数: 55**
- `docs/LIFFフォーム企画案_ゲーム・クーポン・スタンプ等.md` の案 12「次回来店タイミング予測 + 施術記録の共有」と同じもの。こちらは店舗側のカルテが先にあることが前提

**注意点**
- お客様に見せる前提の記録と、店舗内部のメモを**必ず分ける**（案 5 のテンプレートで「お客様に公開」フラグを項目ごとに持つ）

### 案 8: カルテ検索・絞り込み ○

**店舗の使い方**
- 「この薬剤を使った人に注意喚起したい」「担当 A の顧客だけを見たい」「タグ『妊娠中』の人を確認したい」

**設計**
- 一覧の絞り込みに「タグ」「担当」「最終メニュー」「最終来店からの日数」を追加（チップ列に「絞り込み ▾」を足し、シートで条件を選ぶ）
- 検索 API に `tag` / `therapist` / `menu` パラメータを追加。薬剤などテンプレート項目の検索は `chart_data` の JSONB 検索（案 5 の後）

**流用度: ★★★★☆ / 工数: 25**

### 案 9: 来店時のクイック入力（レジ横運用） ○

**店舗の使い方**
- 会計のたびに詳しいカルテを書く余裕が無い店舗向け。**30 秒で「来店 + 金額 + 一言」**だけ記録し、詳細はあとで追記する
- 顧客一覧の各カードに「来店」ボタン。押すと今日の日付・前回と同じメニュー・金額が入った状態で開く

**流用度: ★★★★☆ / 工数: 20**（案 2 の入力シートの簡易版）

---

### 案 10: カルテの印刷 / PDF・CSV △

**店舗の使い方**
- 紙で残したい店舗、スタッフの引き継ぎ、行政の確認（一部の業態）

**設計**
- 顧客詳細の「⋯」メニューに「カルテを PDF で保存」。来店記録・写真（任意）・申し送りを A4 に整形（抽選フォームの企画案で使った HTML → PDF と同じ方法）
- CSV は既存の顧客 CSV に来店記録を追加（アレルギー等の要配慮情報は既定で除外）

**流用度: ★★★☆☆ / 工数: 20**

## 6. 共通で気をつけること

| 項目 | 内容 |
|---|---|
| 要配慮個人情報 | アレルギー・既往歴・体調などは個人情報保護法の要配慮個人情報にあたり得る。取得時に本人の同意が必要。編集フォームに「お客様の同意を得て記録してください」を明記し、プライバシーポリシーに記録の目的を追記。CSV や PDF には既定で含めない |
| 写真 | 顔が写る写真は個人情報。同意の記録（チェック + 日付）を持つ。非公開バケット + 署名付き URL で配信し、公開 URL を作らない。容量上限を店舗ごとに設ける |
| 閲覧権限 | 店舗管理者は自店舗の顧客だけ（既存の RLS と `checkStoreAccess`）。テナント管理者が横断で見る場合はプライバシーポリシーに明記 |
| 監査 | 誰がいつカルテを編集・削除したかを残す（既存のフォーム操作履歴と同じ仕組みを顧客・来店記録に広げる）。削除は理由付きの論理削除も検討 |
| 業態差 | 医療機関の診療録とは異なる（本システムは医療用ではない）。治療院などで法定の記録義務がある場合は、本機能は補助であり法定帳簿の代替にならない旨を利用規約に明記 |
| 既存データ | 予約完了時に自動作成される来店記録（メニュー・金額）はそのまま。カルテ項目は後から追記する形にして、過去データを壊さない |

| # | 質問 | 推奨 |
