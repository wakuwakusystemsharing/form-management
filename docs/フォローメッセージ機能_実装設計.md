**「7. 決定事項」に回答済み（2026-09-08）。同日に実装完了（「9. 実装結果」参照）。リリース手順は `docs/フォローメッセージ_リリース手順.md`。**

1. 基本情報編集画面の「予約リマインダー」の**下**に「フォローメッセージ」の設定ブロックを追加する

5. 再予約済みの人を配信対象から外したうえで、**その再予約を基準にフォローを設定し直す**

## 2. 現状の仕組み（前提知識）

### 2-1. 予約リマインダーの流れ

| 項目 | 現状 |
|---|---|
| 設定の保存先 | `stores` テーブルの 4 カラム: `reminder_enabled` / `reminder_time`（HH:00）/ `reminder_days_before`（1〜7）/ `reminder_template`（JSONB） |
| 設定 UI | `src/app/tenant/[tenantSlug]/admin/[storeId]/page.tsx` の店舗編集ダイアログ内。文面は `src/components/ReminderTemplateEditor.tsx` |
| 文面ロジック | `src/lib/reminder-template.ts`（管理画面プレビュー用）と Edge Function 内のコピー（Deno から `src/` を import できないため二重管理） |
| 送信 | Supabase Edge Function `send-reminders`（`supabase/functions/send-reminders/index.ts`）。pg_cron が**毎時 0 分**に起動し、`reminder_time` が現在時刻（JST）と一致する店舗だけ処理 |
| 対象予約の決め方 | 「今日 + N 日」の `reservation_date` を持ち、`status != 'cancelled'` かつ `line_user_id` がある予約を**その場で検索**して push |
| 送信済みの記録 | **なし**。毎時ちょうど 1 回だけ起動する前提で、同じ予約に二重送信しない設計 |

### 2-2. フォローメッセージに使えない点・注意点

- リマインダーは「予約日」を基準に検索するだけで済むが、フォローは「**予約が成立した日**（または来店日）+ N 日」を基準にし、さらに**その後に再予約があれば止める**必要がある。「その場で検索」方式だと判断材料が増えて複雑になり、送信済み管理が無いので**二重送信・送り漏れの判定ができない**
- Edge Function は 1 本の cron で動いているため、ここにフォローの処理を**足し込む**と、リマインダーのバグがフォローに波及する（逆も同様）
- Web 予約フォーム（`form_type: 'web'`）の予約は `line_user_id` が無いので、LINE では送れない（リマインダーも同じ制約）

## 3. 全体設計

### 3-1. 方針: 「配信予定キュー」方式（推奨）

リマインダーのように毎回検索するのではなく、**予約が成立した時点でフォロー送信の予定行を 1 件作り**、cron はその予定表を見て送るだけにします。

```
予約成立（POST /api/reservations）
  └→ follow_messages に 1 行 INSERT（scheduled_at = 基準日 + N 日 の送信時刻, status = 'scheduled'）
        ※ 同じ顧客（line_user_id）の未送信行があれば 'superseded' にして、新しい行に置き換える（= 再予約で設定し直し）

予約キャンセル（PATCH /api/reservations/{id} / Webhook / LIFF）
  └→ その予約に紐づく未送信行を 'cancelled' に

Edge Function send-follow-messages（毎時 0 分）
  └→ scheduled_at <= 今 かつ status = 'scheduled' の行を取得
       ├ 店舗の follow_enabled が OFF → 'skipped'
       ├ 顧客に「基準日より後の未来予約」がある → 'skipped'（再予約済み。二重チェック）
       ├ line_channel_access_token が無い → 'skipped'
       └ push 成功 → 'sent'（sent_at 記録） / 失敗 → 'failed'（error 記録。翌時間に再試行、3 回で諦める）
```

**この方式のメリット**
- 送信済み・スキップ理由が**行として残る**ので、二重送信しない・問い合わせ時に追える
- 「再予約があったら止める」を **INSERT 時（即時）と送信時（最終確認）の 2 段階**で判定でき、要望 4・5 を確実に満たせる
- リマインダーの Edge Function・cron・カラムには**一切手を入れない**（ぶつからない）
- 将来「来店 1 週間後にクーポン」「誕生日」など別種類の自動配信を同じキューに載せられる

### 3-2. データ構造

**`stores` に追加するカラム（リマインダーと同じ並び）**

```sql
ALTER TABLE stores ADD COLUMN IF NOT EXISTS follow_enabled    BOOLEAN NOT NULL DEFAULT false;  -- 既存店舗に勝手に送らないよう既定 OFF（Q8）
ALTER TABLE stores ADD COLUMN IF NOT EXISTS follow_base        TEXT    NOT NULL DEFAULT 'reservation_date'
                                             CHECK (follow_base IN ('reservation_date','created_at')); -- 基準日: 予約日 / 予約受付日（Q1）
ALTER TABLE stores ADD COLUMN IF NOT EXISTS follow_days_after  INTEGER NOT NULL DEFAULT 7;      -- 基準日から何日後（1〜60）
ALTER TABLE stores ADD COLUMN IF NOT EXISTS follow_time        TEXT    NOT NULL DEFAULT '12:00'; -- 送信時刻（HH:00）
ALTER TABLE stores ADD COLUMN IF NOT EXISTS follow_template    JSONB;                            -- 文面（NULL = デフォルト）
```

**新規テーブル `follow_messages`（配信予定キュー）**

```sql
CREATE TABLE follow_messages (
  id              TEXT PRIMARY KEY DEFAULT REPLACE(uuid_generate_v4()::TEXT, '-', ''),
  store_id        TEXT NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  reservation_id  TEXT NOT NULL REFERENCES reservations(id) ON DELETE CASCADE,
  line_user_id    TEXT NOT NULL,
  customer_id     TEXT,                                  -- 分かれば紐付け（履歴表示用）
  base_date       DATE NOT NULL,                         -- 基準日（店舗の follow_base に従い、予約日 or 予約受付日を INSERT 時に確定）
  scheduled_at    TIMESTAMPTZ NOT NULL,                  -- 送信予定（JST の base_date + N 日 の follow_time）
  status          TEXT NOT NULL DEFAULT 'scheduled'
                  CHECK (status IN ('scheduled','sent','skipped','cancelled','superseded','failed')),
  skip_reason     TEXT,                                  -- 'rebooked' | 'reminder_same_day' | 'store_disabled' | 'no_token' | 'reservation_cancelled'
  attempt_count   INTEGER NOT NULL DEFAULT 0,
  last_error      TEXT,
  sent_at         TIMESTAMPTZ,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_follow_messages_due ON follow_messages (scheduled_at) WHERE status = 'scheduled';
CREATE INDEX idx_follow_messages_store_user ON follow_messages (store_id, line_user_id);
CREATE UNIQUE INDEX uq_follow_messages_reservation ON follow_messages (reservation_id);  -- 1 予約 1 行
```

RLS: 店舗管理者・システム管理者は自店舗分を SELECT のみ（履歴表示用）。INSERT / UPDATE は Service Role（API ルート・Edge Function）だけ。リマインダーと同じ「管理者は見るだけ」の考え方。

**文面テンプレート型（`src/types/store.ts`）**

`ReminderTemplate` と同じ形をそのまま使います（差し込み項目は同じ 8 種類）。デフォルト文言だけがフォロー用になります。

```typescript
export type FollowTemplate = ReminderTemplate;   // { header_title, header_color, body_text, text_color, show_details, footer_text, show_footer }
```

| 項目 | リマインダーのデフォルト | フォローのデフォルト（案） |
|---|---|---|
| ヘッダー | 【予約前日メッセージ】 | 【ご来店ありがとうございました】 |
| 本文 | 明日の予約をお知らせします | 先日はご来店いただきありがとうございました。次回のご予約もお待ちしております |
| 詳細ブロック | 日時・メニュー・担当・お名前 | 同じ（前回の予約内容として表示。OFF にもできる） |
| 末尾 | 心よりお待ちしております | またのご来店を心よりお待ちしております |

### 3-3. 「再予約があったら止める」の判定ルール

**A. 予約成立時（`POST /api/reservations` の直後）**

1. `follow_enabled` が OFF の店舗、`line_user_id` が無い予約（Web 予約・電話番号のみ）→ 何もしない
2. 同じ `store_id` + `line_user_id` の `status = 'scheduled'` 行があれば → すべて `superseded` にする（古い予約を基準にしたフォローは不要）
3. 新しい予約を基準に `scheduled_at` を計算して INSERT

→ これで「再予約済みの方は配信対象から外れ、再予約を基準に設定し直される」（要望 5）

**B. 送信時（Edge Function）— 再予約チェック（Q2）**

- 「止める期間」は別項目にせず、**基準日から送信予定日までの N 日間**（= `follow_days_after`）とする
- `reservations` に「同じ `store_id` + `line_user_id`」「`status != 'cancelled'`」「フォロー元の予約とは別」「`reservation_date` が **基準日より後**」の予約が 1 件でもあれば `skipped`（`rebooked`）
  - 基準日 = 予約日のとき: 来店後〜フォロー送信日までに次回予約が入っていれば止める
  - 基準日 = 予約受付日のとき: 受付後〜送信日までに別の予約が入っていれば止める
  - 送信日より先の予約も「基準日より後」に含まれる（次回予約が既にある人にはお礼ではなくリマインダーが届く方が自然）

→ A で漏れたケース（手動予約・過去データ・A 実行前の予約）も止まる（要望 4）

**B'. 送信時 — リマインダーと同日の回避（Q4）**

- 店舗の `reminder_enabled = true` で、その顧客に `reservation_date = 今日 + reminder_days_before` の未キャンセル予約があれば `skipped`（`reminder_same_day`）
- これは `stores` のリマインダー設定を**読むだけ**で、`send-reminders` のコードには依存しない。判定式（今日 + N 日）は Edge Function 内に同じ 3 行を置く
- 多くの場合 B の「再予約あり」で先に止まるが、基準日 = 予約受付日で N 日後がちょうどリマインド日に当たるケース（同じ予約のフォローとリマインダーが同日）を B' が拾う

**C. キャンセル時**

- 予約が `cancelled` になったら、その予約の `scheduled` 行を `cancelled` に（キャンセルした予約のお礼を送らない）
- 逆にキャンセル解除（`cancelled` → 他）で元に戻す場合は `scheduled` に再作成（キャンセル ↔ 復元の同期は既に `customer_visits` で同じことをやっているので、その隣に追加）

### 3-4. リマインダーとぶつからないための取り決め

| リスク | 対策 |
|---|---|
| Edge Function 1 本に両方入れると片方のバグが波及 | **別 Function `send-follow-messages` を新設**。`send-reminders` は触らない |
| cron ジョブ名の衝突 | `send_follow_messages` という別名で `cron.schedule`。既存の `send_reservation_reminders` はそのまま |
| 同じ日に両方が同じ顧客へ届く（例: 7 日後フォローと 1 日前リマインドが同日） | フォロー側が `stores` のリマインダー設定を読んで**フォローをスキップ**（3-3 B'）。リマインダー側は一切変更しない |
| カラム名の混同 | `reminder_*` と `follow_*` で接頭辞を分ける。型・UI・API も同じ接頭辞 |
| 文面ロジックの二重管理がさらに増える | `src/lib/reminder-template.ts` を**共通化**（`resolveMessageContent(template, ctx, defaults)`）し、リマインダー・フォローの両方で使う。Edge Function 側は各 Function にコピーを置く（現状と同じ運用。ヘッダーのコメントで相互参照） |
| `stores` PUT でカラムが増える | `PUT /api/stores/{storeId}` は body をそのまま update しているので追加作業は不要。**ただし `follow_base` / `follow_days_after` / `follow_time` の値検証をサーバー側に追加**する |
| Local 環境（JSON モード） | Edge Function が動かないのはリマインダーと同じ。キュー行の作成は `data/follow_messages.json` に書き、送信はしない |

## 4. 画面設計

基本情報編集ダイアログの「予約リマインダー」ブロックの**直下**に、同じ見た目のブロックを追加します。

```
┌ フォローメッセージ ─────────────────────────────────┐
│ [トグル] 有効                                        │
│ 予約から設定した日数後に、お礼・次回予約のご案内を     │
│ LINE で自動送信します（通数を 1 消費します）           │
│                                                     │
│ 基準日  (●) 予約日（来店日）から  ( ) 予約受付日から  │
│ 何日後に送る   [ 7日後 ▼ ]   送信時刻 [ 12:00 ▼ ]     │
│ ※ 送信日までに次の予約が入っている方には送りません。   │
│   次の予約を基準に改めてフォローが予定されます。        │
│ ※ 予約リマインダーと同じ日になる場合はフォローを       │
│   送りません。                                        │
│                                                     │
│ ┌ フォロー文面のカスタマイズ ────────────────────┐  │
│ │ （ReminderTemplateEditor と同じ編集 + プレビュー）│  │
│ └────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────┘
```

- 「何日後」の選択肢: 1・2・3・5・7・10・14・21・30・45・60 日後のプルダウン（Q8）
- 「送信時刻」: リマインダーと同じ 07:00〜21:00 の毎時
- `ReminderTemplateEditor` を **汎用化**（`MessageTemplateEditor` に改名し、タイトル文言・デフォルト文言・プレースホルダー説明を props で渡す）。既存のリマインダー呼び出しは挙動を変えない
- 設定はテナント側の店舗編集ダイアログのみ（Q7）。店舗管理者ページには出さない（リマインダーと同じ）
- 配信結果の表示（Q6）: 顧客詳細の予約履歴の各行に「フォロー: 予定 / 送信済み / 再予約のためスキップ / リマインダーと同日のためスキップ / 失敗」の小さなバッジ。`GET /customers/{customerId}` のレスポンスに `follow_message` を同梱する（`customer_reservation_history` が OFF の店舗では出さない）

6. `pnpm type-check` / `pnpm test` / `pnpm lint` → staging で実機確認（Edge Function デプロイ + cron 登録）

| Q8 | 日数の選択肢 / 初期値 | **プルダウン（1〜60 日の代表値）/ 既存店舗は OFF** | `follow_enabled` 既定 false |

## 8. 補足: 想定される質問

**Q. リマインダーの Edge Function を修正せずに済むのは本当ですか？**
はい。テーブル・カラム・Function・cron をすべて別名で追加するため、`send-reminders` は 1 行も変わりません。共通化するのは Next.js 側の `reminder-template.ts` だけで、回帰テストで既存出力を固定します。

**Q. Edge Function が 1 時間止まったら？**
リマインダーは「その時刻に起動しなければ送り漏れ」ですが、フォローは `scheduled_at <= 今` の行を拾うので、次の起動でまとめて送られます（遅れは最大で止まっていた時間分）。3 回失敗した行は `failed` のままにして、無限再試行はしません。

**Q. お客様が LINE をブロックしていたら？**
push が失敗（HTTP 4xx）して `failed` / `last_error` に残ります。リマインダーと同じで店舗への通知はしません。
