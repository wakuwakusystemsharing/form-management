# 寄せ書きウォール 要件定義書

作成日: 2026-10-09 / 状態: 設計案（実装前レビュー用）

公式 LINE のリッチメニューから開く「匿名の付箋コルクボード」を、各店舗の機能として追加する。
店舗管理者ページ・テナント側 店舗ページの **「抽選管理（抽選フォーム）」と「設定」の間** に「寄せ書き」タブを置く。

---

## 1. 目的・ゴール

- お客様が店舗への感想を **匿名の付箋** として貼り、他のお客様の付箋も眺められる場を公式 LINE 内に作る（来店後のエンゲージメント・口コミの可視化）
- 店舗は付箋の一覧と公開 / 非公開を管理できるが、**評価の良し悪しで消すことはできない**（非公開の理由は「規約違反」のみ）
- 匿名性を守りつつ、誹謗中傷や個人情報の投稿には運営が対応できる（識別子はハッシュで内部保存）
- 既存スタック（Next.js App Router / TypeScript / Supabase / LINE LIFF）と既存の認可・タブ制御・local JSON モードの仕組みに乗せ、店舗ごとのコード分岐を作らない

## 2. 現状システムとの整合（前提）

| 既存の仕組み | 本機能での使い方 |
|---|---|
| マルチテナント（`organizations` → `stores.org_id`、店舗 ID は 6 文字 / UUID） | 全テーブルに `store_id`。テナント分離は既存 RLS 関数（`is_master_admin()` / `system_admin_store_ids()` / `store_admins`）を流用 |
| LINE 本人確認 `src/lib/line-verify.ts`（`verifyLineIdToken` / `resolveLineChannelId`。チャネル ID は `stores.line_channel_id` → 環境変数） | 投稿・削除・通報のすべてで LIFF の ID トークンを検証。local は `line_user_id` の申告を許容（抽選と同じ） |
| 店舗単位の管理 API 認可 `src/lib/store-access.ts`（`authorizeStoreAccess`。local はスキップ） | 店舗管理 API はすべてこれで保護 |
| 店舗管理者ページのタブ制御 `src/lib/store-admin-tabs.ts`（`STORE_ADMIN_TAB_IDS` / `stores.admin_visible_tabs`） | タブ ID `walls` を追加（`lotteries` と `settings` の間）。既存の「店舗管理者に表示するメニュー」でも ON/OFF できる |
| ミドルウェア（`/{storeId}/admin` 等のみ保護、それ以外は通す） | お客様向けページ `/wall/{storeId}` は保護対象外のまま公開ページとして動く（LIFF ログインはページ内で行う） |
| お客様向け LIFF ページの実装パターン | 予約 / アンケート / 抽選は静的 HTML（Storage 配信）。本機能は **投稿一覧が常に変わる動的ページ** なので Next.js のページとして実装する（§8.1 で比較） |
| 既存の「LINE 以外のブラウザ制限」（`liff.isInClient()` で案内） | 同じ案内画面を流用（LINE 外では閲覧も投稿も不可） |
| local 環境は `data/*.json` | `data/wall_boards.json` / `data/wall_posts.json` / `data/wall_reports.json` / `data/wall_consents.json` |
| 操作履歴 `form_audit_logs` | 店舗の公開 / 非公開操作は別テーブル `wall_moderation_logs` に残す（フォーム用の監査ログとは混ぜない） |
| 店舗管理者ページの「このページの使い方」（`store-admin-guide.ts`） | 寄せ書きタブ用の説明を追加 |

## 3. 用語

- **ウォール / ボード**: 店舗ごとに 1 つのコルクボード画面。`/wall/{storeId}`
- **付箋（投稿）**: 140 文字以内のテキスト 1 件
- **投稿者ハッシュ**: LINE ユーザー ID から作る識別子（§6.2）。画面・API には出さない
- **公開状態**: `published`（表示中）/ `pending`（承認待ち: 承認制 or NG ワード保留）/ `review`（通報 3 件で確認待ち）/ `hidden`（店舗が規約違反で非公開）/ `deleted`（本人削除）

## 4. 機能要件

### 4.1 お客様向け（ウォール画面 `/wall/{storeId}`）
- **F-01** 公式 LINE のリッチメニュー等から開く。LIFF ログイン後、ID トークンを取得して以降の API に添える。LINE 以外のブラウザは案内画面（既存パターン）
- **F-01b** 店舗設定の公開範囲（§12 #5）に応じて、友だち追加が必要な場合は案内画面を出す（閲覧のみ可の設定では「貼る」ボタンを友だち追加の案内に置き換える）
- **F-02** ボードに付箋を **新しい順** で表示。初回 30 枚、下へスクロールで追加読み込み（カーソル方式）
- **F-03** 「付箋を貼る」ボタン → 入力シート（140 文字、残り文字数表示、テキストのみ。URL・改行は保存するが表示は改行のみ反映、URL はリンク化しない）
- **F-04** 初回投稿時のみ **同意チェック**（文言は §4.3）。未同意では投稿できない。同意済みなら次回以降は出さない（同意記録が規約バージョンと一致する場合）
- **F-05** 自分の付箋には「削除」が出る（本人判定はサーバー側の投稿者ハッシュ一致。画面は API の `is_mine` だけを見る）。削除は確認ダイアログの後に実行
- **F-06** 各付箋に「通報」ボタン → 理由（誹謗中傷 / 個人情報 / 宣伝 / その他）を選んで送信。同じ人が同じ付箋を 2 回通報しても 1 件として扱う。自分の付箋は通報できない
- **F-07** 返信・DM・いいね・コメント・検索・並び替えは作らない。画面は「貼る」「見る」「通報する」だけ
- **F-08** 付箋の **色・傾き・位置ずれ** は投稿 ID から決まる擬似乱数で固定（誰が見ても同じ見た目。再読み込みでも変わらない）
- **F-09** 承認制の店舗では、投稿直後に「お店の確認後に表示されます」と案内。NG ワード保留も同じ案内（NG ワードに当たったことは伝えない）
- **F-10** 店舗がボードを無効にしている / 店舗が存在しない場合は「現在ご利用いただけません」の画面

### 4.2 投稿ルール
- **R-01** 1 ユーザー 1 店舗につき **1 日 N 件まで**（N は店舗設定 `wall_boards.daily_max`、1〜10、既定 1。2026-10-10 変更: 当初は固定 3。JST の日付で判定。`deleted` も数に入れる = 貼って消すを繰り返せない）
- **R-02** 連続投稿は **30 秒以上** あける（同一ユーザー・同一店舗。前回投稿の `created_at` から判定）
- **R-03** **NG ワード** に当たったら `pending`（保留）。NG ワード = 運営共通リスト（`src/lib/wall-ng-words.ts`、部分一致・大文字小文字と全半角を正規化）+ 店舗ごとの追加語（設定）。判定は保存時のみ（既存投稿を遡らない）
- **R-04** 店舗ごとに **即公開 / 承認制** を切り替え（既定: 即公開）。承認制では新規投稿は `pending`
- **R-05** 上限・間隔・NG ワードのエラーは日本語の文言で返す（「本日の投稿は 3 件までです」「30 秒ほど待ってからもう一度お試しください」など）
- **R-06** 文字数 1〜140（前後の空白は除去）。空文字・140 超は 400

### 4.3 匿名の扱い（重要）
- **A-01** お客様画面・店舗管理画面・テナント管理画面のいずれにも **投稿者の名前・LINE ユーザー ID・アイコンを出さない**。API レスポンスにも含めない（`author_hash` も返さない）
- **A-02** DB には投稿者ハッシュだけ保存（§6.2）。マスター管理者であっても画面上で元の LINE ユーザー ID に戻す機能は作らない（対応が必要なときは運営が DB で照合する運用）
- **A-03** 初回投稿時の同意文（規約バージョン `WALL_TERMS_VERSION`、初期値 `2026-10-01`）:
  > 投稿は他のお客さんにもお店にも匿名で表示されます。ただし、規約違反や誹謗中傷があった場合に対応するため、運営が投稿者を内部で記録しています。
- **A-04** 同意は `wall_consents` に **同意日時・規約バージョン・投稿者ハッシュ** で保存。規約バージョンが上がったら再同意
- **A-05** 店舗管理画面の一覧には「投稿 No.（短い ID）」と本文・日時・状態・通報数だけを出す。同じ人の投稿をまとめて見る機能は作らない（匿名性を下げるため）

### 4.4 通報
- **T-01** 通報は `wall_reports` に 1 行（付箋 ID・理由・通報者ハッシュ）。同一通報者 × 同一付箋は一意
- **T-02** 通報が **3 件** に達したら付箋を `review`（確認待ち）にし、**ボードから非表示**。店舗が「公開に戻す」か「規約違反で非公開」を決めるまで保留
- **T-03** 店舗管理画面に「通報あり」の絞り込みと件数バッジ
- **T-04** 通報者には「通報を受け付けました」とだけ返す（結果は通知しない）

### 4.5 店舗管理者ページ（`/{storeId}/admin` → 「寄せ書き」タブ。抽選管理と設定の間）
- **M-01** 付箋一覧: 状態（すべて / 表示中 / 承認待ち / 確認待ち / 非公開 / 本人削除）と通報ありで絞り込み。本文・日時・状態・通報数・通報理由の内訳。50 件ずつ「さらに読み込む」
- **M-02** 操作: 「公開する」（`pending` / `review` / `hidden` → `published`）、「非公開にする」（理由は **「規約違反」のみ**。選択式で他の選択肢は無い。確認ダイアログに「評価の良し悪しを理由に非公開にはできません」の注記）
- **M-03** `deleted`（本人削除）は復元不可・本文は「（投稿者が削除）」表示にしない。一覧では件数に数えるだけで本文は非表示（本人の意思を尊重）
- **M-04** 設定（同タブ内のカード）: ボードの有効 / 無効、即公開 / 承認制、見出し文・サブ見出し、世界観プリセットと付箋色、店舗ごとの NG ワード追加、公開 URL（リッチメニュー設定用）とコピー
- **M-05** ダッシュボードの数字カードに「寄せ書き（今週の投稿数 / 確認待ち）」を追加（ボード有効時のみ）
- **M-06** 「このページの使い方」の説明（`STORE_ADMIN_GUIDES.walls`）

### 4.6 テナント側 店舗ページ（`/tenant/{slug}/admin/{storeId}` → 「寄せ書き」タブ。抽選フォームと設定の間）
- **N-01** 店舗管理者ページと同じ一覧・操作・設定（弊社が代行する前提）
- **N-02** 加えて「このボードを有効にする」の初期設定と、リッチメニュー用 URL の案内
- **N-03** 設定タブ「店舗管理者に表示するメニュー」に「寄せ書き」が増える（`admin_visible_tabs`。未設定 = 表示）

### 4.7 世界観（店舗ごとのパラメータ。構造・コードは分岐しない）
- **W-01** `wall_boards.theme`（JSON）で切り替え: `preset`（`cork` / `wood` / `paper` / `chalkboard`）、`background_color`（プリセットの上書き用 HEX）、`note_colors`（HEX 配列、3〜8 色。既定は黄・ピンク・水色・緑・オレンジ）、`font`（`rounded` / `standard` / `handwriting`）、`title`（見出し。既定「みんなの寄せ書き」）、`subtitle`（既定「お店への感想を匿名で貼れます」）、`placeholder`（入力欄の例文）
- **W-02** 画面は theme を CSS 変数（`--wall-bg` / `--note-colors` / `--wall-font`）に展開するだけ。プリセット追加は定義ファイル `src/lib/wall-themes.ts` に 1 件足すだけで済む
- **W-03** 店舗の `theme_color` をアクセント（ボタン・見出し）に使う（既存フォームと同じ）

### 4.8 演出
- **E-01** 新しく貼った付箋は上から落ちて着地（CSS keyframes、0.5 秒、`prefers-reduced-motion` では無効）
- **E-02** 付箋は -4°〜+4° の傾きと数 px の位置ずれ（§6.3 の擬似乱数）
- **E-03** タップで少し浮く（`transform: translateY(-4px) scale(1.02)` + 影）。長押し・ドラッグはしない
- **E-04** 画像・外部ライブラリを使わず CSS だけで実装。1 画面 30 枚で 60fps を目標（`transform` / `opacity` のみアニメーション、`will-change` は貼る瞬間だけ）
- **E-05** LINE 内ブラウザ（iOS / Android）で動作確認。横幅 320px でも 2 列で崩れない

## 5. 非機能要件
- **P-01** 一覧 API は店舗 + 状態 + 作成日時のインデックスで 50ms 以内（1 店舗 1 万件を想定）
- **P-02** 投稿 API は ID トークン検証（LINE への問い合わせ）を含めて 1 秒以内
- **S-01** すべての API で `store_id` の一致を検証。付箋 ID だけで他店舗の付箋に触れない
- **S-02** 投稿者ハッシュの秘密鍵は環境変数（§6.2）。未設定時は投稿 API を 500 で止める（匿名性を守れないため）
- **S-03** XSS 対策: 本文は保存時にプレーンテキストとして扱い、表示時にエスケープ（React の既定）。URL はリンク化しない
- **L-01** local 環境（`NEXT_PUBLIC_APP_ENV=local`）は JSON ファイルで一通り動く（`pnpm dev` で確認できる）
- **O-01** 投稿・削除・通報・店舗の操作はサーバーログに付箋 ID と結果だけ出す（ユーザー ID・本文は出さない）

## 6. データ設計（Supabase）

### 6.1 テーブル
```sql
-- 店舗ごとのボード設定（1 店舗 1 行）
wall_boards (
  store_id TEXT PRIMARY KEY REFERENCES stores(id) ON DELETE CASCADE,
  enabled BOOLEAN NOT NULL DEFAULT false,
  moderation TEXT NOT NULL DEFAULT 'instant' CHECK (moderation IN ('instant','approval')),
  theme JSONB NOT NULL DEFAULT '{}',          -- §4.7（欠損は既定値で補完）
  ng_words TEXT[] NOT NULL DEFAULT '{}',       -- 店舗ごとの追加 NG ワード
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
)

-- 付箋
wall_posts (
  id TEXT PRIMARY KEY,                         -- 12 文字ランダム（既存のフォーム ID と同じ生成）
  store_id TEXT NOT NULL REFERENCES stores(id) ON DELETE CASCADE,
  body TEXT NOT NULL CHECK (char_length(body) BETWEEN 1 AND 140),
  status TEXT NOT NULL CHECK (status IN ('published','pending','review','hidden','deleted')),
  pending_reason TEXT,                          -- 'approval' | 'ng_word'（pending のとき）
  author_hash TEXT NOT NULL,                    -- §6.2。API には出さない
  report_count INTEGER NOT NULL DEFAULT 0,      -- wall_reports の件数キャッシュ（DB 関数で更新）
  hidden_reason TEXT,                           -- 'terms_violation' のみ（hidden のとき）
  hidden_at TIMESTAMPTZ, hidden_by UUID,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
)
INDEX (store_id, status, created_at DESC)
INDEX (store_id, author_hash, created_at DESC)  -- 1 日 3 件 / 30 秒の判定用

-- 通報
wall_reports (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id TEXT NOT NULL,
  post_id TEXT NOT NULL REFERENCES wall_posts(id) ON DELETE CASCADE,
  reason TEXT NOT NULL CHECK (reason IN ('abuse','personal_info','advertising','other')),
  reporter_hash TEXT NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (post_id, reporter_hash)
)

-- 同意
wall_consents (
  store_id TEXT NOT NULL,
  author_hash TEXT NOT NULL,
  terms_version TEXT NOT NULL,
  agreed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (store_id, author_hash, terms_version)
)

-- 店舗の公開 / 非公開操作の記録
wall_moderation_logs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  store_id TEXT NOT NULL, post_id TEXT NOT NULL,
  action TEXT NOT NULL CHECK (action IN ('publish','hide')),
  reason TEXT,                                  -- hide のとき 'terms_violation'
  actor_user_id UUID, actor_email TEXT, actor_role TEXT,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
)
```
- **RLS**: すべてのテーブルで有効。ポリシーを付けるのは `wall_boards`（抽選と同じ 3 階層: マスター / システム管理者 = 自テナント / 店舗管理者 = 自店舗）だけ。`wall_posts` / `wall_reports` / `wall_consents` / `wall_moderation_logs` はポリシー無し（service_role 経由のみ）。`wall_posts` には `author_hash` があり、店舗管理者が Supabase のクライアントから直接読めると同じ人の投稿を突き合わせられてしまうため、管理画面も必ず API（投稿者情報を返さない）を通す
- **`wall_boards.liff_id`**: 寄せ書きは静的 HTML ではなく Next.js のページ `/wall/{storeId}` で表示し、店舗ごとに LIFF アプリ（エンドポイント URL = このページ）を作る。管理画面に「ページの URL」と「リッチメニュー用（https://liff.line.me/{liff_id}）」を表示
- **DB 関数の実行権限**: `wall_insert_post_checked` / `wall_add_report` は anon / authenticated から EXECUTE を取り消し、service_role だけが呼べる
- **ハッシュの鍵**: 環境変数 `WALL_AUTHOR_HASH_SECRET`（32 文字以上。staging / production 必須。local は固定値で代替）。店舗 ID を混ぜた HMAC-SHA256 なので、店舗をまたいだ同一人物の突き合わせもできない
- **DB 関数** `wall_add_report(post_id, reporter_hash, reason)`: 通報の重複チェック → 件数更新 → 3 件で `review` に変更、を 1 トランザクションで行う（同時通報でも 3 件ちょうどで切り替わる）
- **DB 関数** `wall_insert_post_checked(...)`: 1 日 3 件 / 30 秒間隔の判定と挿入を 1 トランザクションで（抽選の `lottery_insert_entry_checked` と同じ考え方）
- local: 同じ判定を `src/lib/wall-repository.ts` の JSON 実装で行う（送信はしない）

### 6.2 投稿者ハッシュ
- `author_hash = HMAC-SHA256(key = WALL_AUTHOR_HASH_SECRET, message = store_id + ':' + line_user_id)` の hex
- 店舗 ID を混ぜるので、同じ人でも店舗が違えばハッシュが異なる（店舗をまたいだ突合をできなくする）
- 環境変数 `WALL_AUTHOR_HASH_SECRET`（32 文字以上）。staging と本番で別の値。ローテーションは想定しない（変えると本人削除ができなくなるため、変える場合は要手順）
- `.env.local.example` と `docs/SETUP.md` に追記

### 6.3 見た目の擬似乱数
- `seed = FNV-1a(post.id)`、`mulberry32(seed)` で 3 つ引く: 色 = `note_colors[floor(r1 * n)]`、傾き = `-4 + r2 * 8` 度、横ずれ = `-6 + r3 * 12` px
- 純粋関数 `src/lib/wall-layout.ts`（Vitest）。サーバーとクライアントで同じ結果

## 7. API 設計

共通: レスポンスに `author_hash` / `reporter_hash` / LINE ユーザー ID / 表示名を **含めない**。エラーは `{ error: '日本語' }`。

### 7.1 お客様向け（公開 API。ID トークン検証）
| メソッド / パス | 内容 |
|---|---|
| `GET /api/walls/{storeId}?cursor=&limit=30&id_token=` | ボード設定（theme / moderation / enabled / 規約バージョン / 同意済みか）+ `published` の付箋（新しい順、カーソル）。各付箋は `{ id, body, created_at, is_mine }`。`id_token` 無しでも閲覧は可（`is_mine` は全て false、同意済みは false） |
| `POST /api/walls/{storeId}/posts` body `{ id_token, body, consent: { agreed: true, terms_version } }` | 投稿。初回は同意が必要（未同意 = 428 + `consent_required`）。上限 / 間隔は 429、NG ワード / 承認制は 201 + `status: 'pending'`。返す付箋に `is_mine: true` |
| `DELETE /api/walls/{storeId}/posts/{postId}` body `{ id_token }` | 本人削除（ハッシュ一致のみ。他人は 404 で存在も教えない） |
| `POST /api/walls/{storeId}/posts/{postId}/report` body `{ id_token, reason }` | 通報。自分の付箋は 400。重複は 200（新規扱いしない） |

### 7.2 店舗管理（`authorizeStoreAccess`）
| メソッド / パス | 内容 |
|---|---|
| `GET /api/stores/{storeId}/wall/settings` / `PUT` | ボード設定（enabled / moderation / theme / ng_words）。`PUT` で theme と NG ワードを検証（色 HEX、3〜8 色、NG ワード 1 語 30 文字・100 語まで） |
| `GET /api/stores/{storeId}/wall/posts?status=&reported=1&cursor=&limit=50` | 一覧（本文・状態・通報数・理由内訳・日時）。`deleted` は本文を返さない |
| `PATCH /api/stores/{storeId}/wall/posts/{postId}` body `{ action: 'publish' }` または `{ action: 'hide', reason: 'terms_violation' }` | 公開 / 非公開。`reason` が `terms_violation` 以外は 400。`wall_moderation_logs` に記録 |
| `GET /api/stores/{storeId}/wall/stats` | 今週の投稿数・承認待ち・確認待ち（ダッシュボード用） |

## 8. 画面設計

### 8.1 お客様向けページの実装方式（比較と結論）
| 方式 | 長所 | 短所 |
|---|---|---|
| A. 静的 HTML を Storage に配信（予約 / 抽選と同じ） | 既存の配信・キャッシュ・`line_only` の仕組みをそのまま使える | 付箋一覧は毎回 API で取るので静的化の利点が薄い。世界観の変更ごとに再デプロイが必要 |
| B. **Next.js のページ `/wall/{storeId}`（クライアントコンポーネント）** | 設定変更が即反映、演出の実装・改修が速い、デプロイ不要。ミドルウェアは保護対象外なのでそのまま公開できる | LIFF 初期化と LINE 外の案内はページ内で実装（既存の静的 HTML から流用） |

→ **B を採用**。URL は `https://（システムの URL）/wall/{storeId}`。LIFF の Endpoint URL にこれを登録し、リッチメニューから開く。

### 8.2 お客様向け画面の構成
- ヘッダー: 見出し / サブ見出し（theme）
- ボード: 2 列（320〜479px）/ 3 列（480px〜）のマソンリー風。付箋は正方形に近い角丸、色・傾き・ずれは §6.3
- 右下固定「付箋を貼る」ボタン → 下から出る入力シート（テキストエリア、残り文字数、初回のみ同意チェック、「貼る」）
- 付箋タップ → 少し浮く + 右上に「⋯」→「通報する」（自分のものは「削除」）
- 下端で追加読み込み。空のときは「最初の付箋を貼ってみませんか？」

### 8.3 店舗管理（店舗管理者ページ / テナント側 店舗ページ共通コンポーネント）

## 10. テスト要件
- **匿名性**: 公開 API・店舗管理 API の全レスポンスに `author_hash` / `reporter_hash` / `line_user_id` / 表示名が **含まれない**（キーの存在を再帰的に検査するテスト）
- **本人削除**: 別のユーザー（別ハッシュ）からの削除は 404。本人は 200。削除後は一覧に出ない
- **店舗分離**: 他店舗の付箋 ID を指定した取得 / 削除 / 通報 / 公開操作がすべて 404
- **ルール**: 1 日 3 件（JST 日付の境界）、30 秒間隔、140 文字、NG ワード保留、承認制で `pending`
- **通報**: 同一人物の重複は 1 件、3 件で `review` かつ一覧から消える、自分の付箋は通報不可
- **公開操作**: 非公開理由が `terms_violation` 以外は 400、記録が残る
- **見た目**: 同じ投稿 ID は常に同じ色・傾き（`wall-layout`）
- **local**: JSON モードで投稿 → 一覧 → 削除が一通り通る（一時ディレクトリで隔離）

### 12.1 決定を受けた追加・変更点
- `wall_boards` に `access_mode TEXT NOT NULL DEFAULT 'login' CHECK (access_mode IN ('login','friend_to_post','friend_only'))` を追加（§6.1）
- 公開 API `GET /api/walls/{storeId}` のレスポンスに `access_mode` を含め、画面側で「友だち追加が必要です」の案内（既存の抽選フォームの文言を流用）を出す。`POST .../posts` は `access_mode` が `friend_to_post` / `friend_only` のとき `line_friend_flag !== true` なら 403
- NG ワードは語句リスト + 形式判定（URL・メールアドレス・電話番号・@ から始まる ID）で「保留」にする。保留理由は `pending_reason = 'ng_word'` で、店舗画面では「NG ワード」とだけ表示（どの語に当たったかは表示する: 店舗が判断しやすいため）
- ダッシュボードの数字カードは「確認待ち（通報）」「承認待ち」を分けて表示
