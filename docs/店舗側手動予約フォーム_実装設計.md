# 店舗側手動予約フォーム 実装設計

作成日: 2026-08-27 / 更新: 2026-08-25（敵対的検証の指摘を反映）/ ステータス: 実装済み（staging 検証待ち）

## 1. 背景・目的

電話や他媒体で受けた予約を店舗が Google カレンダーに直接書き込むと、**システム上に予約データが存在しない**ため、お客様が公式 LINE で「予約確認」「予約をキャンセル」を送信しても「現在ご予約はありません。」と返されてしまう。

これを解決するため、**店舗側がお客様（LINE 友だち）を指定して代理で予約を登録できるフォーム**を追加する。予約は通常の予約 API を通って DB と Google カレンダーに登録され、選択した友だちの LINE 識別 ID（userId）が予約に紐付くため、以後の「予約確認」「予約をキャンセル」が正しく機能する。

### 最重要の安全要件

**間違ったお客様（友だち）に予約が紐付いてはならない。** 紐付けを誤ると、他人の予約内容がそのお客様の「予約確認」に返されてしまう。対策は §6 参照。

## 2. 全体像

```
店舗管理者ページ（/{storeId}/admin）
  予約管理 → フォーム管理 → 各予約フォームカード（LINEタイプのみ）
    └ [店舗側手動予約フォーム] ボタン（開く/コピーの上）
         ↓ 新しいタブで開く
GET /api/stores/{storeId}/forms/{formId}/manual-form   ← 認証必須（店舗管理者）
  → StaticReservationGenerator を「手動モード」で実行した HTML を返す
       ・最上部に「お客様選択」（必須）… LINE友だちを選ぶ or「LINE紐付けなしで登録」
       ・LIFF は読み込まない / LINE メッセージは送信しない
       ・送信ボタンは「予約を行う」
         ↓ お客様選択の友だち一覧
GET /api/stores/{storeId}/line-friends                 ← 認証必須（店舗管理者）
  → 店舗のチャネルアクセストークンで LINE の友だち一覧＋プロフィールを取得
  → 未認証アカウント等で取得できない場合は「LINE連携済みの顧客一覧」にフォールバック
         ↓ 送信（manual_entry: true 付き）
POST /api/reservations（既存 + 手動登録向けの分岐を追加）
  → DB に予約作成（line_user_id = 選択した友だちの userId / LINEなし登録は null）
  → Google カレンダーにイベント作成（既存処理）
  → 顧客（customers）への紐付け（手動 + LINE ID ありのときは LINE ID のみで照合 → §3.5）
```

## 3. 各コンポーネントの設計

### 3.1 手動フォーム HTML（StaticReservationGenerator の手動モード）

`generateHTML(config, formId, storeId, mode?: 'manual')` に第4引数を追加。
既存のフォーム生成を丸ごと再利用するため、**メニュー・スタッフ選択・カレンダー〇✕・希望日時・カスタムフィールド等の挙動は通常フォームと完全に同一**。手動モードでは以下だけが変わる:

| 項目 | 通常（LIFF） | 手動モード |
|---|---|---|
| LIFF SDK / liff.init | 読み込む | **読み込まない**（`typeof liff === 'undefined'` の既存ガードで送信処理は自然にスキップ） |
| お客様選択欄 | なし | **フォーム最上部に必須表示**（LINE友だち選択 or LINE紐付けなし） |
| お名前欄 | 設定（show_customer_name）に従う | **常に表示**（登録相手を記録するため） |
| 希望日時モードの必須選択 | 設定（required_choices）に従う | **第一希望のみ必須**（電話で確定済みの1日時を登録できるように） |
| 送信ボタン | 予約する | **予約を行う** |
| 送信時の LINE メッセージ | LIFF で送信 | **送信しない** |
| 送信前確認 | なし | **選択中のお客様名を明示した確認ダイアログ** |
| 予約 API への line_user_id | LIFF から取得した本人の userId | **選択した友だちの userId**（LINEなし登録は null） |
| 予約 API への manual_entry | なし（false） | **true**（サーバー側の CRM 照合・流入経路の扱いが変わる） |
| localStorage への保存/復元 | あり | **保存しない**（スタッフ端末に前回のお客様情報を残さない） |
| DB 登録失敗時 | LINE 送信を優先して続行 | **エラーを表示して中断**（成功画面を出さない） |

- ヘッダーに「店舗側手動予約フォーム（スタッフ用）」のバナーを表示し、通常フォームと視覚的に区別する。
- 友だち選択時、お名前欄が空なら自動入力（顧客名 > LINE 表示名）。電話番号も顧客情報にあれば自動入力（いずれも手修正可能）。
- 設定の変換（お名前欄の強制表示・第一希望のみ必須）は生成時のコピーに対して行い、元のフォーム設定は変更しない。

### 3.2 友だち一覧 API `GET /api/stores/{storeId}/line-friends`

- **認証**: `getCurrentUser` + `checkStoreAccess`（顧客 API と同じ。local 環境はスキップ）
- **取得手順**:
  1. `stores.line_channel_access_token` を取得（未設定なら 400 とガイダンス）
  2. LINE Messaging API `GET /v2/bot/followers/ids` をページング取得（上限 1,000 人で打ち切り、打ち切り時はレスポンスに `truncated: true`。打ち切りは API の到着順であり名前順ではない）
  3. 各 userId の表示名・アイコンを `GET /v2/bot/profile/{userId}` で取得（並列 10、取得失敗＝ブロック中等はスキップ）
  4. `customers` テーブル（line_user_id 一致）と突合し、顧客名・電話番号を付与
- **フォールバック**: followers API が 403 等で使えない場合（**未認証の公式アカウントでは友だち一覧を取得できない LINE 側の仕様**）は、`customers` テーブルの LINE 連携済み顧客（line_user_id あり）を一覧として返す。レスポンスの `source: 'followers' | 'customers'` で UI に区別を伝え、フォールバック時は「未認証アカウントのため、過去にフォームを利用したお客様のみ表示しています」と案内する。
- **レスポンス**:

```json
{
  "source": "followers",
  "truncated": false,
  "friends": [
    {
      "line_user_id": "U1234...",
      "display_name": "山田太郎",
      "picture_url": "https://...",
      "customer_name": "山田 太郎",   // customers 突合（なければ null）
      "customer_phone": "090..."      // 同上
    }
  ]
}
```

- **キャッシュ**: サーバー側でストア単位・TTL 5 分のメモリキャッシュ（プロフィール取得の API 負荷軽減。サーバーレスのため保証はなくベストエフォート。友だち追加直後のお客様は最大 5 分表示されない）。

### 3.3 手動フォーム配信 API `GET /api/stores/{storeId}/forms/{formId}/manual-form`

- **認証**: 友だち一覧 API と同じ（店舗管理者のみ）。未認証は JSON の 401 を返す。
- フォームを DB から取得 → `normalizeForm` → `generateHTML(config, formId, storeId, 'manual')` → `text/html` で返す。
- 対象フォームが LINE タイプでない場合は 400（手動フォームは LINE 識別 ID の紐付けが目的のため）。
- `Cache-Control: no-store`（常に最新の設定で表示）。

### 3.4 店舗管理者ページ

- フォーム管理欄の各予約フォームカード（**LINE タイプのみ**）に「店舗側手動予約フォーム」ボタンを追加（開く/コピーの上）。クリックで `/api/stores/{storeId}/forms/{formId}/manual-form` を新しいタブで開く。
- 予約一覧（ダッシュボード・予約管理の一覧/テーブル）で、手動登録した予約に「**店舗登録**」バッジを表示（LINE紐付けなしは「店舗登録（LINEなし）」）。

### 3.5 予約 API `POST /api/reservations` の手動登録向け分岐

通常フォームと同じペイロードに `manual_entry: true` が付く。サーバー側は以下を行う（`manual_entry` が無い通常予約の挙動は不変）:

| 処理 | 通常予約 | 手動登録 |
|---|---|---|
| 識別フラグ | なし | `customer_info.entry_source = 'staff_manual'` を**サーバー側で強制付与**（後から手動登録と識別・監査できる） |
| CRM 顧客照合 | `line_user_id` → 電話番号 の順 | **LINE ID あり: `line_user_id` のみ**（電話番号では照合しない）/ LINE なし: 電話番号で照合 |
| 流入経路 `source_medium` | ブラウザから推定して保存 | **保存しない（null）**（スタッフのブラウザ環境が分析に混入しないように） |
| 同時予約数上限の判定 | LINE ID + 電話番号 | LINE ID あり: LINE ID のみ / LINE なし: 電話番号 |
| DB 保存・カレンダー作成・スタッフ自動割当・来店履歴 | 既存処理 | 既存処理（同一） |

これにより Webhook の「予約確認」「予約をキャンセル」は `line_user_id` で検索するため、**追加実装なしで**手動登録の予約が返されるようになる。

**共通の修正（通常予約にも適用）**: 電話欄非表示フォームのフォールバック値「未記入」を CRM 照合キーから除外（`customer-utils.ts`）。従来は「未記入」の別顧客が 1 人だけ存在すると、新規 LINE ユーザーの予約がその顧客に紐付く潜在バグがあった。

## 4. お客様選択 UI（手動フォーム内・vanilla JS）

- 検索ボックス + 候補リスト（LINE アイコン画像・LINE 表示名・顧客名/電話（突合できた場合））のドロップダウン。名前・顧客名・電話番号でリアルタイム絞り込み。表示は最大 50 件（超過分は「検索で絞り込んでください」と案内）。
- 選択すると候補リストは閉じ、**選択中カード**（アイコン + LINE 表示名 + 顧客情報 + [変更] ボタン）を表示。
- **「LINE紐付けなしで登録」ボタン**: LINE を使っていない・ブロック中のお客様の電話予約用。識別 ID なしで登録され「予約確認」の対象外になる旨をカード・確認ダイアログ・完了画面の 3 箇所で明示。お名前は必須。
- 選択必須: 未選択で「予約を行う」を押すと「お客様を選択してください」でブロックし、お客様選択欄へスクロール。

## 5. 「予約確認」が正しく返る仕組み（本機能の目的の検証）

1. 手動フォームで友だち U123 を選択して予約 → `reservations.line_user_id = 'U123'` で保存
2. お客様（U123）が公式 LINE で「予約確認」を送信
3. Webhook は `store_id + line_user_id = U123` で未来の予約を検索 → 手動登録した予約が返る ✓
4. 「予約をキャンセル」も同様に本人の予約のみが対象になる ✓
5. LINE紐付けなしで登録した予約は `line_user_id = null` のため、誰の「予約確認」にも返らない（意図どおり）

## 6. 誤紐付け防止策（安全要件への対応）

1. **視覚確認**: 候補リストと選択中カードに LINE のプロフィール画像・表示名・（判明していれば）顧客名/電話を表示し、同姓同名でも見分けられるようにする
2. **送信前の確認ダイアログ**: 「以下のお客様の予約として登録します。LINE表示名: 〇〇 / 顧客名: 〇〇。よろしいですか？」で最終確認。キャンセルで中断できる
3. **userId はサーバー取得値のみ**: 候補は友だち一覧 API が返した userId に限定し、手入力はさせない（タイプミスによる誤紐付けを構造的に排除）
4. **完了画面に登録先を表示**: 送信後の完了画面に「〇〇様の予約として登録しました」を表示し、直後に気付けるようにする
5. **スタッフ端末に残さない**: 手動モードでは localStorage への保存・復元を行わない（前回のお客様情報の引き継ぎ事故を防止）
6. **CRM を電話番号で混線させない**: LINE ID ありの手動登録は電話番号で顧客照合しない（電話番号の共有・入力ミスで別人の顧客レコードに紐付き、LINE 表示名が上書きされる事故を防止）
7. **「LINE紐付けなし」を明示的に用意**: 該当する友だちがいないときに「似た名前の別人」を選ぶ誘因を無くす
8. **手動登録の識別フラグ**: `entry_source = 'staff_manual'` + 管理画面バッジで、万一の誤登録を後から追跡・監査できる

## 7. エッジケース

| ケース | 挙動 |
|---|---|
| チャネルアクセストークン未設定 | 友だち一覧 API が 400。フォーム上に「LINE設定が必要です」を表示。「LINE紐付けなしで登録」は使用可能 |
| 未認証の公式アカウント（followers API 403） | LINE 連携済み顧客一覧にフォールバック + 案内文を表示 |
| 友だち 0 人 / 連携済み顧客 0 人 | 「表示できるお客様がいません」を表示。「LINE紐付けなしで登録」は使用可能 |
| LINE を使っていない・ブロック中のお客様 | 「LINE紐付けなしで登録」で登録（予約確認の対象外であることを明示） |
| プロフィール取得失敗（ブロック中など） | その友だちは一覧から除外（メッセージも届かないため予約紐付けの意味が薄い） |
| 友だち 1,000 人超 | API 到着順で打ち切り（`truncated: true` を案内）。見つからない場合は検索で絞り込むか、LINE紐付けなしで登録 |
| 同じ LINE 表示名の友だちが複数 | アイコン画像と顧客情報（突合できた場合）で区別。区別できない場合は確認ダイアログで再確認 |
| 手動登録で入力した電話番号が別の顧客と一致 | LINE ID ありなら電話番号照合をしないため別人に紐付かない（新規顧客として作成） |
| 同一ユーザーの同時予約数上限に到達 | 既存の 409 エラーをそのまま表示（意図的な上限設定を手動でも尊重） |
| Web タイプのフォーム | 手動フォームボタンを表示しない（API 側でも 400） |
| ログイン期限切れで手動フォームを開いた | 友だち一覧が 401 → 「店舗管理画面を開き直してください」を表示 |

## 9. スコープ外（将来の拡張候補）

- 手動予約の登録時に、お客様の LINE トークへ push メッセージで予約内容を通知する（現状は通知しない。勝手にメッセージが届くことを避けるため、必要になったら店舗ごとの ON/OFF 設定として追加する）
- 友だち一覧のサーバーサイド検索・ページング（1,000 人超の大規模アカウント向け）
- 候補リストへの「最終予約日」「識別 ID 末尾」の併記（同名の友だちの判別補助）

## 10. 敵対的検証の記録（2026-08-25）

| 指摘 | 重大度 | 対応 |
|---|---|---|
| 電話番号一致で別の顧客レコードに紐付き、LINE 表示名が上書きされる（CRM 混線） | 🔴 | 手動 + LINE ID ありは LINE ID のみで照合（§3.5）。通常予約の「未記入」一致バグも修正 |
| 手動登録した予約を後から識別できない | 🟠 | `customer_info.entry_source='staff_manual'` をサーバー側で強制付与 + 管理画面バッジ。`source_medium` は保存しない |
| LINE 友だちでないお客様を登録できない（別人を選ぶ誘因） | 🟠 | 「LINE紐付けなしで登録」を追加（対象外である旨を 3 箇所で明示） |
| 希望日時モードで確定済みの 1 日時を登録しにくい | 🟡 | 手動モードは第一希望のみ必須 |
| 1,000 人超の打ち切り・同名の判別・5 分キャッシュ | 🟡 | 案内文と検索で運用対応。改善案は §9 に記載 |
